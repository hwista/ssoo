## 검수 기준

원천 데모 실행 코드와 현재 SSOO 구현을 메뉴별로 비교한다. 과거 [패리티 매트릭스](source-parity-matrix.md)의 완료 기록은 참고 자료이며 현재 일치 판정을 대신하지 않는다. 각 메뉴는 조회 조건·필드/표·계산·입력 검증·저장/재조회·차수/확정·삭제/취소·권한·빈 상태/실패 복구·다른 메뉴 반영을 해당 기능에 맞게 검수한다.

결과는 `일치`, `합의된 차이`, `불일치`, `판정 대기`로 기록하고 코드 대조와 실제 실행 증거를 구분한다. 원천 자체의 모순이나 SSOO 확장은 근거 없이 오류 또는 합의된 차이로 처리하지 않는다. 발견한 차이를 바꾸는 작업은 검수와 구분한다.

사업연도의 CRM 소유와 공통코드 저장소/모듈의 플랫폼 소유는 사용자와 합의된 구조 변경이다. 코드 의미와 도메인 기능의 소유까지 공용화한 것으로 해석하지 않는다. 공용 실행 DB의 이전 전 상태로 현재 코드의 기능 일치를 판정하지 않는다.

## 1차: 대시보드 수정 전 진단

실제 메뉴 경로는 `/?sourceSurface=dashboard`다. 일반 홈과 이 화면은 계산 경로가 다르므로 일반 홈의 API만 검사해서 대시보드 메뉴를 통과시키지 않는다.

원천 `app.globals.js`, `app.list.js`, `supabase_client.js`의 SHA-256은 기존 `REF-01` manifest와 모두 같다. 아래 차이는 이번에 제공 원본이 변경되어 발생한 것이 아니다.

| ID | 항목 | 데모 실행 코드 | 수정 전 SSOO | 수정 전 코드 대조 결과 |
|---|---|---|---|---|
| DASH-01 | 확정 집계 차수 | 확정된 행을 먼저 고른 후 그룹별 최대 차수 선택 | 그룹별 최신 차수 조회 후 확정 여부 필터 | 불일치: 확정 1차 + 미확정 2차에서 데모는 1건, SSOO는 0건 |
| DASH-02 | 절사 적용 | 대시보드는 수량×단가 원값 합계 | 저장 시 절사된 `line.amount` 합계 | 불일치: 수량 3 × 단가 12,345, 절사 1,000이면 데모 37,035원 / SSOO 37,000원 |
| DASH-03 | 최근 목록 순서 | `getLatestPerGroup()` 반환 배열을 역순으로 바꿔 5건 | `updatedAt` 내림차순으로 5건 | 불일치: 동일 표본에서 ID 3,2,1 / 1,2,3. 원천 방식의 업무상 타당성은 별도 판정 |

### 기존 기록의 해석 정정

기존 매트릭스는 원천 확정 지표를 “최신 차수 중 확정”으로 설명하지만, 실제 `getConfirmedLatest()`는 **확정된 차수 중 최신**을 선택한다. 서로 다른 동작이다. 또한 원천 최근 목록을 “최신 수정순”으로 설명한 부분은 실제 `reverse()` 구현과 다르다. `SRC-05`, `SRC-07`, `SRC-10`, `UX-01`은 이 차이를 재검수하기 전 현재 완료로 인용할 수 없다. 과거 실행 기록 자체는 보존한다.

### 증거와 한계

- 재현 스크립트: `output/crm-menu-audit/dashboard-code-probe.cjs`
- 결과와 파일 해시: `output/crm-menu-audit/dashboard-code-probe.json`
- 실행: `node output/crm-menu-audit/dashboard-code-probe.cjs`
- 원천 함수와 현재 화면의 계산식을 직접 추출해 실행했다. 절사 금액도 서버의 현재 `resolveLineAmount`를 추출해 계산했다. 화면·API·DB를 거치는 종단간 증거는 아니다.
- 기존 dashboard/opportunity 단위 테스트 2개 묶음, 36개 통과. 이 테스트의 통과로 위 원천과의 차이가 해소되지는 않는다.
- 작업 전 `pnpm run codex:preflight` 통과. 제품 코드와 DB 데이터 변경 없음.

## 대시보드 수정 및 재검증

사용자가 확인된 차이의 수정을 승인했다. 위 표와 코드 추출 증거는 **수정 전 진단 기록**이며 현재 구현의 실패 결과가 아니다.

- `OpportunityService.listSourceDashboardOpportunities`가 활성 전체 차수에서 그룹별 최신 행과 그룹별 최신 확정 행을 따로 선택한다. 최신 미확정 행이 이전 확정 행을 가리지 않는다.
- 대시보드 API는 매출 2종·원가 3종의 수량×단가 원값을 합산한다. 화면도 같은 API 집계를 사용하고, 소수 수량에서 나온 원 단위 소수값을 임의로 정수 반올림하지 않는다. 견적/계약 계산과 SSOO 운영 지표는 기존 DC·절사 후 금액을 유지한다.
- 원천의 숫자 그룹 ID 열거 순서는 SSOO에서 그룹 최초 행의 숫자 ID 순서에 대응한다. 최근 목록은 그 그룹 순서를 역순으로 최대 5건 선택한다. 수정일 변경이나 기존 그룹의 새 차수 생성으로 그룹의 등록 순서를 바꾸지 않는다.
- 기존 대시보드 응답의 `sourceCompatibility.calculationBasis`는 `latest-confirmed-version-raw-total`로 명시한다. 화면에서 최신 목록만 보고 재집계하던 코드를 제거했다.

검증 기록: `output/playwright/crm-dashboard-fix/`.

- 서버 전체 88묶음·619테스트 통과. 이번에 추가한 6테스트는 이전 확정/최신 미확정, 복수 확정 중 최신 선택, 그룹 등록 순서, 5개 라인 분류의 절사/DC 전 합계, 최근 5건, 빈 집계를 포함한다.
- 격리 DB에 launch migration 14개와 전체 seed/trigger를 적용했다. 원천 `app.globals.js`의 실제 함수를 실행해 DB에서 읽은 같은 표본의 기대값을 구하고 API와 비교했다.
- 실제 요청 23개, 원천 함수와 대조 8상태 통과: 원천 표본, 새 미확정, 확정, 새 차수, 미확정 수정, 새 차수 확정, 확정 해제, 정리 후 원상 복구. 관리자·조회 계정과 비인증/조회 계정 쓰기 거부도 포함한다.
- 전체 seed 기준: 8그룹·확정 6건·매출 1,526,500,000원·원가 1,081,370,000원·이익 445,130,000원·이익률 29%. 원천 6그룹 부분집합은 확정 4건·매출 1,269,500,000원이다.
- CRM production build 통과. 공용 실행 DB는 변경하지 않았다.
- 실제 브라우저: 동일 DB 표본으로 원천 HTML/함수를 실행한 대시보드와 SSOO의 4개 지표·최근 5건 순서 일치. 관리자/조회 계정, 상세 클릭, 재진입/새로고침, 1440×1000/390×844 화면을 확인했다. 모바일 가로 넘침 없음.
- 실제 브라우저에서 절사·DC가 있는 소수 수량 건을 생성/확정한 뒤 **1,526,537,096.5원**을 확인했다. 미확정 새 차수를 생성해도 이 금액을 유지하고 최근 목록의 링크는 새 차수를 가리킨다. 검증 건 삭제 후 원래 금액 복구를 확인했다.
- 제품 브라우저 console warning/error·page error·HTTP 4xx/5xx 없음. 상세 이동/새로고침 중 RSC 요청 취소 2건은 별도 기록했다. 원천은 Supabase에 접속하지 않는 읽기 전용 표본 실행이며, 원천 로그인/쓰기 검증을 주장하지 않는다.
- 화면 증거: `source-desktop.png`, `target-desktop.png`, `target-mobile.png`, `viewer-mobile-recent.png`, `fractional-confirmed.png`, `fractional-new-draft.png`. 세부 실행 결과는 `verification.json`에 모았다.

다음 메뉴는 영업기회 현황이다. 그 화면의 절사 전 계산·정렬은 이번 대시보드 수정으로 자동 해결됐다고 간주하지 않고 별도로 대조한다.

### 현재 검증 증거와 남은 조건

`output/playwright/crm-business-plan-performance-20261002/`에 실행 스크립트·결과·스크린샷을 보존한다. Docker/WSL 장애와 PostgreSQL `ECONNREFUSED` 때문에 사용자는 런타임 복구를 다른 세션에 맡기고 독립 작업을 계속하도록 지시했다. **이 메뉴는 실 API·DB·실제 MDI 통합 검증 완료로 집계하지 않는다.** Docker 배포는 실행하지 않았다.

- `source-results.json`: 원천 함수와 실제 컴파일한 CRM 서비스 계산을 같은 표본으로 10개 연도/필터 조합에서 대조했다. 0원·월 상쇄·계획 없는 계약·WBS 없는 이름/계약 구분을 포함한다. 저장소만 fixture이며 실제 DB/API 호출이 아니다. 원천 입력의 WBS 대문자 정규화와 미선택 사전 필터는 승인된 SSOO 정책을 명시적으로 적용했다.
- 관련 사업계획/DTO/보고 서버 29테스트와 계약 청구계획 존재 여부 1개 표적 테스트를 통과했다. 최종 DTO 주석 추가 후 사업계획/DTO 24테스트를 다시 통과했다. 타입 패키지·CRM 격리 production 빌드 및 변경 CRM 경로 lint를 통과했다. 이후 필터 라벨 연결/숫자 열 폭 수정은 실제 컴포넌트 브라우저에서 검증했다.
- `harness-verify-results.json`: 실제 CRM 컴포넌트를 별도 Next 화면에 올려 fixture API 응답으로 **20검사**를 통과했다. 개별 셀 819개·전체 합계 3행, 공통코드 표시명, 확정 차수, 즉시 필터·미선택·빈 연도, 조회 503 재시도, active prop 재활성화 조회, 지연 응답 차단, 데스크톱 고정 열과 모바일 가로 스크롤을 포함한다. runtime exception 0건, 주입한 조회 503은 예상 오류다. 1440×1000/390×844 화면을 직접 확인했다. 로그인·실제 셸 탭 전환·저장 후 반영 검증을 대체하지 않는다.

복구 후 재시작 해시 9개 일치와 이전 11차 검수 DB 삭제를 확인했다. 별도 DB `ssoo_business_plan_performance_20261002`, API 4310, CRM 3536에서 기존 복사본이 아닌 현재 소스의 격리 production 빌드로 검증을 재개했다.

### 유지한 차이·검증 한계·다음 범위

원천은 이메일 선택 입력, 비밀번호 trim/완화된 길이, 임시 비밀번호 평문 표시를 사용한다. SSOO의 이메일 필수·기존 강도 정책·재설정 메일 outbox를 유지하며 동일 동작이나 이번 신규 합의로 집계하지 않는다. 새 계정의 가입 승인 절차도 유지한다. 인증 검증용 두 계정만 격리 DB에서 승인 상태를 설정했으므로 이번 검증은 가입 승인 UI를 검증한 것이 아니다. 메일 worker를 끈 상태에서 생성한 실제 outbox가 pending인 것을 확인했으며 메일 발송/수신·재설정 코드 완료 흐름은 이번 검증 범위가 아니다.

원천 비활성 확인의 담당 영업기회 개수 안내, 역할/직책의 표현, 행 아바타 등의 세부 표현 차이는 남아 있다. 원천 Supabase 쓰기나 모든 앱의 개인 설정 브라우저 검수를 주장하지 않는다. 개인 설정의 SNS 프로필/계정 프로필은 기존 별도 요청이므로 두 저장의 원자성을 보장하지 않는다. 전체 사용자 목록은 여러 페이지 조회이며 동시 다른 관리자의 생성/삭제에 대한 DB snapshot 일관성까지 보장하지 않는다.

데스크톱 1440×1000·모바일 390×844에서 페이지 가로 넘침 없음과 스크롤 후 작업 버튼 접근을 확인했다. 한국어 문구는 DOM으로 검사하며 WSL Chromium의 글꼴 제한 때문에 시각적 동일성 판정과 구분한다. 운영 Docker에 배포하지 않았다.

이로써 **아직 한 번도 검수하지 않은 메뉴는 0개**다. 기존 메뉴의 DC/원장 정책·Word 서식·실패 조합·세부 표현 등 판정 대기는 해소됐다고 집계하지 않는다. 다음 작업은 새 메뉴가 아니라 이 대장에 남은 불일치/판정 대기 항목을 근거와 함께 회수하는 것이다.
