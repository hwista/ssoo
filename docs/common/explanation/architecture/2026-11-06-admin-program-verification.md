# Admin 프로그램 설계·구현 검증 기록

> 판정: 정의한 인수 범위 통과 · 범위: Admin 공통 관리 17개. [설계](2026-11-06-admin-program-design.md)와 [인수 기준](2026-11-06-admin-program-test-spec.md)에 따른 검증 기록이다. 임의의 모든 운영 상황을 100% 보장한다는 의미는 아니다.

> 후속 사용자 검수에서 설명 증가와 역할 경계의 불명확함이 다시 지적됐다. 이 문서의 기능 통과는 당시 검증 기록으로 보존하며, 최신 적용·완료 판정은 [역할 경계·사용성 재검증](2026-11-06-admin-boundary-acceptance.md)을 따른다.

## 적용 결과

기존 17개 프로그램의 역할과 메뉴를 유지했다. 사용자·조직 상세는 연결 요약과 담당 프로그램 이동을 제공하며 소속·이용권·권한 편집을 중첩하지 않는다. 각 프로그램은 전달받은 대상 조건을 실제 조회와 신규 입력에 사용한다. 인증·메뉴·권한 API·DB 스키마·외부 제공자 설정은 변경하지 않았다.

조직에는 계층 경로·검색·하위 추가와 부모 순환 선택 방지를, 관계 편집에는 대상 검색과 기간 검증을 적용했다. 역할에는 추가/제거 차이·전환 취소·초안 revision 보존을, 정책에는 미저장 상태·적용값 복원·조회 갱신 보호를 적용했다. 메일·AI는 자기 프로그램 안에서 업무를 선택하며 전환 중 폼을 유지한다. 이력은 변경 항목/전체 항목 비교와 대상 조건을 유지하는 관리 화면 복귀를 제공한다.

## Ralph 반복에서 수정한 결함

1. **대상 연결:** 사용자/조직 상세의 중첩 관리 편집을 담당 프로그램 연결로 바꾸고, URL의 사용자·조직·앱 조건을 실제 쿼리와 폼에 적용했다. 이력에서 돌아가는 링크도 문맥을 유지한다. 조직 필터가 없는 신청 API의 링크는 ‘전체 담당 범위 신청 확인’으로 명시했다.
2. **이력 상세 가림:** 전체 필드를 펼쳤을 때 버튼이 검색 영역 뒤로 넘어갔다. 브라우저 좌표와 `elementsFromPoint`로 가림을 확인했다. 공용 second panel의 높이를 위치 기준 부모에 제한하고 내부 스크롤을 유지했다. desktop/mobile에서 버튼 클릭과 패널 경계 검사를 다시 통과했다.
3. **역할 저장 피드백/초안:** 저장 재조회로 성공 안내가 사라지는 문제를 수정했다. 초안을 편집하는 동안 서버 조회가 초안과 최초 revision을 덮어쓰지 않게 했고, 실제 동시 저장 409로 검증했다. 역할 변경·명시적 새로고침의 입력 폐기 확인과 저장 중 일괄 선택 잠금도 유지한다. 전수 이미지 검토에서 비활성 역할이 첫 항목이면 초기 선택되는 문제도 발견해 활성 기본 역할을 우선하도록 수정했다.
4. **정책 적용 시점:** 설정 저장 후 재조회를 기다리고 미저장 폼을 보호한다. 입력 라벨과 실제 필드 연결도 보완했다.
5. **기간 입력:** 소속의 역전 기간, 이용권·권한·위임의 지난 종료일을 저장 전에 설명한다. 기간을 자동 삭제하여 무기한으로 바꾸지 않는다.

타입 검사에서 발견한 optional 목록 접근/배너 prop 문제와 검색 inventory 40→42 불일치도 수정했다. 프로그램 책임·문맥/인코딩·기간 경계는 `verify-admin-program-navigation.mjs`에 회귀 조건으로 추가했다.

시험 코드 자체의 실패도 원본 증거에 남겼다. 드롭다운의 label/role 조회 차이, 숨겨진 MDI 탭의 텍스트 선택, 검색 debounce 이전 다중 행 선택, 회수 기록의 ‘위임 재부여’ 이름, 공용 500 오류 문구를 원문과 혼동한 경우를 보정했다. 실패 주입 해제 전에 다음 시험으로 진행한 실행은 해당 구간의 합격 증거에서 제외하고 조회 복구·이동·종료 구간을 따로 다시 통과했다. 배포 재시작 중 연결이 끊긴 시험도 재실행했다. 강제 클릭으로 버튼 가림을 우회하지 않았다.

## 구조·회귀 검토

- 사용자·조직 연결 컴포넌트는 다른 프로그램의 편집 패널을 import하지 않는다. 접근 진단의 연결 창도 편집 대신 담당 프로그램 이동을 제공한다.
- 기존 17개 route·메뉴·legacy route·탭 재사용·탭 한도 복구와 공용 recipe·제목·한글 경로를 검사했다.
- 새 검색 두 곳은 기존 `SsooSearchInput`을 사용하며 Codex/GitHubDocs 규칙과 42개 입력 inventory를 동기화했다.
- 공용 변경은 실제 결함이 확인된 상세 패널의 높이/스크롤로 한정했다. Admin 전용 문맥 조합은 Admin에 남겼다. 본 작업 전 소스 보존본과 비교하여 이전 작업을 덮어쓰지 않았음을 점검했다.
- 서버와 5앱 플랫폼 검사, Admin 타입·lint·배포 빌드, frame/UI 소비/스타일/입력/오류 복구, 문서·규칙 동기화 검사를 실행했다. 서버 114 suite / 872 tests는 플랫폼 guard의 기존 캐시가 재사용됐으며 신규 서버 테스트를 실행했다고 계산하지 않는다. 이번 Admin 처리는 실제 브라우저/API로 검증했다.
- desktop 1440×1000 / mobile 390×844의 17개 프로그램 34개 화면에서 제목·경로·recipe·본문 높이·행 작업·도움말·가로 넘침과 HTTP/console/runtime를 검사했다. 마지막 이력 동선 수정 후 해당 동선과 34개 화면 재검수를 통과했다(HTTP/console/runtime 오류 0). 마지막 역할 초기 선택 수정도 desktop/mobile에서 활성 기본 역할·기존 체크 상태·저장 비활성을 확인했다. 인증 세션 확인용 POST는 역할 변경 요청과 구분해 검사했다. 최종 수치는 증거 요약 파일에 기록한다.

## 시험 자료 정리

전용 사용자 `20`, 조직 `2554/2555`, 역할 `651`, AI 작업 `1421~1424`를 비활성화했다. 후속 대기 작업은 취소했으며 원본 실패 상태와 오류는 보존했다. 활성 소속·이용권·사용자/조직 권한·승인 위임은 모두 0건이다. 신청 `20~23`은 승인/반려로 종결됐고 전용 코드 `16409/16410`은 삭제했다. 전용 복구 요청은 소비 처리했다.

인증 정책은 변경 전 값과 비교해 복원을 확인했고 메일 연결 설정은 변경 전 객체와 동일하다. 전용 로컬 시험 메일과 감사 이력은 보존한다. 로컬 수신함은 기존 24시간 보관 정책을 따른다. 정리 검사의 inactive 관계도 감사 기록으로 남는다는 계약과 BigInt 출력 처리를 보정한 뒤 최종 정리 검사를 통과했다.

## 증거와 한계

증거 루트: `output/playwright/admin-program-design-20261106/`.

- `verification-summary.json`: 32개 검증 묶음과 최종 화면·정리 결과
- `audit-last.txt`: 역할 초기 선택 수정까지 포함한 마지막 배포본의 34개 화면 결과
- `relations-flow.txt`, `operations-proof.txt`, `authority-final.txt`: 관계·계정·권한·승인·코드·로컬 메일·AI 실제 처리
- `edge-proof.txt`, `membership-final.txt`, `supplement-proof.txt`: 저장 실패·중복·실제 revision 충돌·조회 복구·이동·회수·추가 처리
- `role-initial-verified.txt`: 비활성 역할이 먼저 반환되어도 활성 기본 역할을 선택하는 최초 진입 회귀
- `policy-proof-final.txt`, `final-navigation.txt`: 정책 원복, 상세 패널 복구, 이력 복귀·새로고침, 모든 메일/AI 업무 선택
- `cleanup.json`: 소유 fixture만 정리한 결과와 설정 복원

실제 배포는 기존 `http://localhost:3000`을 갱신했다. 새 서버나 포트를 추가하지 않았다. 외부 SMTP 수신자에게 전달되는 성공과 유료 임베딩 실행 성공은 검증하지 않았다. 로컬 메일 보관·재시도, AI 작업 재등록과 연결 상태 표시는 실제 동작으로 확인했다. 향후 외부 환경이 준비되면 별도 연결 인수 시험이 필요하다.
