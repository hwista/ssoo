# Admin 운영 UI 개선과 Ralph 검증

> 2026-11-06 · 공통 관리 17개 프로그램 · 기존 localhost:3000

## 완료 기준

템플릿 적용 여부만으로 완료하지 않는다. 운영자가 대상과 현재 상태를 읽고 필요한 조치를 수행할 수 있는지 확인한다.

1. **정보 밀도**: 긴 설명은 제목 옆 ‘사용 안내’로 열고 닫는다. 짧은 데이터 목록은 실제 행 높이만 사용하고, 긴 목록은 본문 안에서 스크롤한다. 페이지 이동이 가려지면 실패다.
2. **상태와 조치**: 상태는 한국어로 읽을 수 있어야 한다. 접근 불가 진단은 서버의 판정 사유와 다음 확인 동선을 함께 제공한다. 실제 API 값만 사용한다.
3. **문맥 유지**: 사용자 상세에서 소속·이용권·권한 예외·이력을 같은 사용자 조건으로 확인한다. 진단에서 계정 복구로 이동할 때 해당 사용자와 검색 조건을 유지한다.
4. **업무 용어**: 기능명과 상태가 내부 코드·개발 용어로만 표시되지 않아야 한다. 추적에 필요한 원본 코드와 식별자는 상세 정보에서 보존한다.
5. **모바일 조작**: 390×844에서 대상·상태·작업 버튼을 가로 스크롤 없이 함께 확인한다. 나머지 필드는 ‘상세 정보’로 보존한다. 편집 창과 오류 복구도 검증한다.
6. **회귀 방지**: 17개 모두 제목·경로·기존 recipe와 주요 조회/폼 진입을 검사한다. 관련 HTTP·프록시·콘솔·런타임 오류는 실패다. 오류 주입 실험은 정상 실행과 분리한다.

## 구현 경계

- 새 화면 템플릿을 복제하지 않는다. `web-shell`의 기존 Workspace/DataWorkspace/Settings와 DataGrid에 opt-in 기능을 추가한다.
- `compact`는 제목의 사용 안내를 펼치는 방식으로 제공한다. 데이터 화면의 주요 작업·검색 조건 토글을 같은 제목 영역에 모으고, 모바일에서는 제목·안내와 작업을 나눠 배치한다. 기존 소비처의 기본 설명 표시를 유지한다.
- `fitContent`는 데이터 페이지의 실제 내용 높이를 사용한다. `fitViewport` 목록은 남는 공간까지 빈 행으로 확장하지 않는다.
- `mobileSummaryColumns`는 같은 열 renderer와 action handler로 모바일 요약 및 부가 필드를 렌더링한다. 앱이 표시할 필드를 지정하고, 데이터·권한·변경 요청 로직은 복제하지 않는다.
- 사용자 관리의 기본 숨김 열은 ‘표시 항목’에서 복원할 수 있다. 모바일 상세에는 해당 필드를 모두 보존한다.
- DB, API 권한 판정, 유료 외부 연결 설정은 변경하지 않는다. 기존 사용자/조직 데이터는 화면 검증을 위해 임의 수정하지 않는다.

## 검증 기록

증거 경로: `output/playwright/admin-ux-20261106/`.

- 기준선: 기존 17개 × 데스크톱·모바일 전체를 `baseline.txt`와 화면 캡처로 기록했다.
- 1차 구현: 위 적용표에 따른 공용 조립, 목록 표현, 문맥 연결, 용어와 운영 화면 순서를 수정했다.
- 1차 브라우저 결과: 34개 화면의 목록 높이·페이지 이동·모바일 요약은 통과했다. 모바일 인증 정책의 제목이 좁아지고, 사용자 화면의 작업·열 선택 줄이 공간을 많이 사용하는 문제가 남아 재수정했다.
- 2차 수정: 제목·작업 통합, 모바일 열 선택 숨김(부가 정보는 상세에 보존), 메일/AI 지표 2열 배치, 권한 명세의 운영 용어 정리를 적용했다. 고정 대상은 목록 로딩 중에도 선택 상태를 표시하며, 소속 재배치에서 종료된 날짜를 새 배치로 복사하지 않는다.
- 추가 시각 검토: 변경 이력과 최근 메일 표의 열 너비를 줄여 오른쪽 작업 버튼이 보이도록 보완했다. 모바일 메일의 상태 문구 줄바꿈을 막고, 연결 설명은 펼치는 안내로 보존하여 대기·처리·실패 지표를 먼저 표시했다.
- 검사 안정화: 초기 조회의 고정 650ms 대기로 인해 권한 목록 로딩 중을 그리드 누락으로 판정했다. 최종 검사는 실제 그리드/사용자 검색 입력과 선택 옵션의 준비를 기다린 후 수행한다. 검사 조건을 바꾸기 전 실패 기록도 보존한다.
- 구조 검토 및 정리: 공통 패키지는 표시·배치만 담당하고 Admin이 요약 열과 업무 동선을 지정한다. 기존 조회 훅·처리 패널·서버 판정을 재사용하며 새 API나 별도 모바일 처리 로직은 추가하지 않았다. 권한 코드·식별자·설명·영향 사용자·재시도 동선은 상세/안내에서 보존했다.
- 최종 화면 검사: `audit-final.txt` — 17개 × 데스크톱 1440×1000/모바일 390×844, 총 34개 통과. 제목·한글 경로·recipe·안내 토글·목록/페이지 이동·짧은 목록 높이·모바일 요약·가로 넘침과 변경 이력/최근 메일 작업 버튼 위치를 확인했다. 콘솔·런타임·HTTP 오류 0건.
- 오류 복구 검사: `recovery-final.txt` — 브라우저에서만 소속 조회 503을 주입해 오류 표시와 다시 시도를 확인했다. 재배치 폼의 사용자/조직 유지, 시작·종료일 초기화, 처리 사유 필수 조건을 확인했다. 예상하지 않은 HTTP 오류는 없었으며 실제 저장은 하지 않았다.
- 프로그램별 동선: `flows-final.txt` — 17개 모두 조회·검색/필터·등록/편집 폼·기록 상세 등 해당 프로그램의 주요 진입을 통과했다. HTTP·런타임 오류 0건.
- 연결/모바일 동선: `journeys-final.txt` — 사용자 → 소속/이용권 → 고정 사용자 권한 예외 → 이력 → 진단 → 같은 계정 복구, 숨긴 열 복원, 역할 영향/안내, 모바일 기록 상세/이력, 검색 조건 요약·빈 상태 복구·배치 폼, 메일/AI 현황 우선 표시 등 6개 통과. HTTP·런타임 오류 0건.
- 검증의 범위: 실제 로컬 조회 API와 기존 데이터를 사용했다. 저장·회수·역할 변경·메일 발송·AI 작업 실행은 이번 UI 검수에서 수행하지 않았다. 이 결과는 위 화면·동선의 완료 근거이며 모든 운영 시나리오의 성공 보장은 아니다.
- 저장소 검사: `codex:preflight`, `codex:verify-sync`, Admin lint/타입, web-shell 빌드, UI 소비/스타일 경계, 입력 의도 40개, frame(5앱 및 Admin 17개 recipe/메뉴), 코드 패턴, 문서 계약과 변경 파일 whitespace 검사를 통과했다.
- 플랫폼 검사: `codex:platform-guard` 통과. 서버·Admin/CRM/PMS/DMS/SNS 빌드, DMS 계약, GitLab 배포 계약 검사를 통과했다. 서버 테스트는 114 suite/872건의 기존 통과 캐시를 재사용했다. 캐시 로그에 기존 worker 종료 경고가 있으며 이번 UI 변경의 신규 실패는 아니다. 전체 로그는 `platform-guard.txt`에 보존한다.
- 적용/정리: 관리형 기존 Admin 컨테이너를 갱신해 `http://localhost:3000`에서 healthy와 최종 화면을 확인했다. 검증용 로그인 세션은 정상 로그아웃 후 브라우저를 닫았다. 새 앱 포트나 별도 개발 서버를 추가하지 않았다.
- 최종 판정: 위 여섯 완료 기준의 지정 화면·동선 검증을 통과했다. 기계 판정 요약은 `verification-summary.json`, 화면 비교는 `baseline.txt`, `after-*.png`, `review-*.jpg`, 동선 증거는 `flow-*.png`, `journey-*.png`, `recovery-*.png`에 있다.
