# Admin 역할 경계와 사용성 재검증

> 판정: 정의한 역할·경계·사용성 인수 범위 통과 (2026-11-09). 전체 17개 프로그램과 영향 동선을 검수했다. 이 판정은 임의의 모든 운영 상황에 대한 보장이 아니다.
> 범위: Admin 공통 관리 17개와 담당 프로그램으로 연결되는 동선. 기존 포트 사용, 외부 유료 호출 없음.

## 설계와 기능 이동 계약

변경 책임은 담당 프로그램 하나에 둔다. 다른 화면에서는 판단에 필요한 상태 요약과 대상이 유지되는 명시적 이동을 제공한다. 기존 템플릿을 유지하며 본문·목록·작업 우선순위를 업무별로 구성한다. 기존 기능의 목적지, 권한, 오류 복구를 보존한 뒤 진입을 전환한다.

## 브라우저 인수 명세

도구: playwright-cli. 실제 기존 localhost:3000, 필요 시 CRM 3001. 전체 17개를 1440×1000과 390×844에서 확인한다. 이전 캡처는 비교 기준만으로 사용한다.

- 각 주소에 직접 진입: 제목, 현재 대상, 데이터 상태, 명시적인 주 작업, 필터, 페이지 이동이 보인다. 주요 작업을 찾기 위해 사용 안내를 열 필요가 없다.
- 사용자 → 정보 수정: 기본정보만 편집한다. 사용자 → 소속 관리/계정 복구: 사용자 ID와 표시 대상이 같고 새로고침 후에도 유지된다. 계정 상태 변경은 계정 화면에서만 실행된다.
- 소속/이용권/예외: 기본 목록에서 종료·회수 자료가 앞을 차지하지 않는다. 종료·회수 필터에서 기록과 재부여를 찾는다. 기간 역전·만료 입력 오류 후 값이 보존된다.
- 역할: 활성 역할의 권한이 처음부터 선택되어 있고 변경 전 저장은 비활성. 변경 차이·영향·사유 확인, 저장 후 재조회와 복원을 실제 수행한다.
- 진단: 사용자 선택 후 계정·소속·앱 판정과 원인별 연결을 확인한다. 대상이 변경되면 이전 판정이 섞이지 않는다.
- 변경 이력: 업무 변경과 전체 기록을 전환하고 세션 분류를 직접 조회한다. 페이지 총건수는 서버의 같은 범위와 일치한다. 상세 전후 비교와 담당 프로그램 복귀를 확인한다.
- 코드: Admin 플랫폼 코드만 편집 가능. CRM 설정에서 도메인 코드 생성·수정·비활성/재활성·삭제·참조 확인을 전용 fixture로 실행하고 복구한다. 기존 코드 참조 조회와 권한 거부를 보존한다.
- 정책/메일/AI: 설정 변경 차이와 실패 복구를 확인한다. 운영 현황에서 설정 편집 없이 상태를 이해할 수 있다. 메일은 로컬 시험만, AI는 외부 생성 호출 없이 전용 작업의 조회·재시도 경로를 검증한다.
- 모든 저장 검증은 전용 fixture 또는 원본 값 snapshot을 사용하며 처리 후 복원한다. 예산이 필요한 외부 전달·모델 호출은 완료 증거에 포함하지 않는다.

실패 조건: 주요 기능 은닉, 중복 편집 책임, 대상 문맥 유실, 상태 의미 오표시, 잘못된 총건수, 입력 소실, 복구 동선 누락, 모바일 핵심 정보 은닉, 관련 API/프록시 실패, 콘솔 warning/error 및 런타임 오류. 의도적으로 주입한 실패는 정상 검사와 분리하고 복구까지 확인한다.

## 반복 검증

1. 기준선의 위반과 원인을 기록한다.
2. 담당 위치·주 작업·조회 범위를 수정하고 타입/린트/관련 서버 시험을 수행한다.
3. 전체 화면의 내용과 실제 처리 흐름을 검수한다. 횟수가 아니라 남은 위반을 기준으로 수정한다.
4. 책임 경계와 중복 표현을 다시 검토하고 불필요한 추상화·설명을 정리한다.
5. 마지막 수정 후 전체 영향 동선과 브라우저 오류 검사를 다시 실행한다. 필수 preflight/sync/platform/docs 검사를 완료하고 결과·제한을 기록한다.

## 검수에서 발견해 보완한 항목

- 사용자 기본정보·계정 조치의 담당 화면을 구분하고 주요 작업을 글자 버튼으로 노출했다. 계정과 이력에서 사용자로 복귀할 때 정확한 사용자 ID도 전달한다. 서버에서 해당 ID를 조회하므로 첫 페이지 밖의 대상도 유지된다.
- 비활성·없는 역할의 이력에서 다른 활성 역할을 대신 편집하게 되는 fallback을 막았다. 요청 대상의 상태, 이력, 조건 해제를 제공한다. 마지막 실제 왕복 검수에서 목적지 `/roles?tab=grants`를 pathname과 비교하지 않아 역할 ID가 빠지던 문제도 수정했고 비활성 역할의 이력 왕복을 재검증했다.
- 승인 담당자 추가에서 같은 담당자·범위의 위임을 다시 저장하면 409가 발생하던 흐름은 기존 위임의 변경/재부여로 연결했다. 기존 revision과 동일한 처리 함수를 사용한다.
- CRM 코드 프록시의 JSON Content-Type 누락으로 실제 저장이 400으로 실패했다. 전달 헤더를 수정하고 실제 route 코드의 본문·감사 필드·인증 전달 회귀 검사를 추가했다. 브라우저에서 목적지 처리가 성공해야 이동 완료로 판정한다.
- 조직 재활성화 실패가 표시되지 않던 기존 누락은 해당 조직 행의 작업 옆에 오류를 표시하도록 보완했다. 재활성화 버튼을 유지해 재시도할 수 있다.
- 변경 이력은 서버에서 업무 범위를 적용한 뒤 총건수와 페이지를 계산한다. 실제 DB에서 관리자 ID가 남은 자동 로그인 갱신 121건을 확인해 generic `UserAuth.update`/`updateMany`도 기본 업무 범위에서 제외했다. 전체 기록·개별 분류에서는 보존한다. 화면의 기록 범위와 분류도 실제 조회 범위에 맞춰 함께 바뀐다.
- 모바일의 조직 상태 작업, 이용권·권한 기간, 메일 처리 상태, AI 작업 지표를 확인하며 아이콘에만 의존하거나 상태 의미를 오인하는 표현을 보완했다. Admin/CRM 코드에는 접힌 필터에서도 현재 유형·상태를 알 수 있도록 기존 템플릿의 짧은 조회 범위 표시를 사용한다. 플랫폼 코드 유형은 사용자 역할·사용자 상태·직급/직책 등 업무명으로 표시하고 실제 코드 식별자는 편집/상세에서 확인한다. 계정 화면의 사용자 관리 이동에서 추가를 뜻하는 아이콘도 제거했다.

책임 경계 재검토: 공용 템플릿은 배치와 표현만 담당한다. 사용자/조직 상세는 상태 요약과 담당 프로그램 연결을 제공하고 관계 편집기를 중첩하지 않는다. CRM 업무 코드는 CRM 설정에서 처리하고 Admin에는 플랫폼 코드 편집과 앱 코드 참조를 둔다. 설명은 중복을 줄이되 권한 제한·기간·차단 효과·실패 복구는 해당 작업에서 유지한다.

증거 루트는 `output/playwright/admin-boundaries-20261106/`이다. 최초 실행에서 틀린 텍스트·숨겨진 탭 선택·화면 크기 변경 직후 캡처로 실패한 시험은 합격 증거로 쓰지 않았다. 표준 서버 오류 문구와 실제 접근성 이름을 기준으로 보정하고 다시 수행했다. 의도적으로 주입한 503과 권한 거부 403은 정상 요청 실패와 분리해 기록했다. 승인·반려 실행은 두 건 모두 성공했지만 뒤따른 시험 코드의 이용권 확인 URL이 잘못되어 404가 났다. 이 실패 기록을 보존하고 실제 서버 경로로 별도 재조회하여 승인한 CRM만 유효함을 확인했다.

최종 배포 후 17개 프로그램의 데스크톱 1440×1000 / 모바일 390×844, 총 34개 화면을 다시 검사했다. 관련 HTTP·console·runtime 오류 0건, 배치 실패 0건이며 화면 이동에 따른 요청 취소는 별도 기록한다. `audit-final-proof.json`, `final-review-desktop-0..2.jpg`, `final-review-mobile-0..2.jpg`와 `verification-summary.json`에 결과를 남겼다. 모든 최종 이미지 묶음도 직접 검토했다.

## 구조·표현 재검토와 검증 범위

- 담당 변경 로직은 기존 API/서비스를 재사용하며 새 시나리오 화면을 만들지 않았다. 관련 정보는 요약하고 편집은 담당 화면에 남겼다.
- 공용 recipe와 원자는 배치·표현을 담당한다. CRM 코드는 CRM 설정의 자체 모듈에 두고 Admin 거대 조건 분기에 흡수하지 않았다.
- 핵심 작업은 글자 버튼, 관련 이동은 도착 프로그램 이름과 이동 표식으로 구별했다. 상시 설명은 줄이고 입력 조건·영향·실패는 해당 작업 위치에 남겼다.
- 데스크톱/모바일의 전체 17개 프로그램 본문을 읽고 화면 이미지도 검토했다. 자동 크기·넘침 검사만으로 사용성을 판정하지 않았다. 비활성 역할 복귀와 CRM 모바일의 조회 유형 표시를 마지막으로 보완한 후 영향 동선을 재검증했다.
- 서버+5앱 플랫폼 guard는 115 suites / 876 tests와 production builds를 통과했다. 이후 최종 변경의 Admin/CRM 빌드·타입/린트, 이력/사용자 조회 관련 13개 시험, preflight, 규칙 sync를 확인했다. 마지막 국소 수정 후 전체 서버 시험을 다시 실행한 것으로 계산하지 않는다.
- 예산 제약에 따라 외부 SMTP 전달, Microsoft 제공자 연결, 유료 임베딩 성공은 미검증이다. AI는 큐 재등록과 연결 상태까지만 확인했고 worker를 활성화하지 않았다. 각 앱의 나머지 도메인 화면 전체는 이번 Admin 공통 범위에 포함하지 않는다.

저장 공간 장애는 [저장소 유지보수 기록](../../guides/storage-maintenance.md#2026-11-09-자동-점검-진입-오류와-수동-공간-반환)에 별도로 기록했다. 자동 Check 진입 오류와 실제 예약 실행 성공, 수동 공간 반환과 컨테이너 복원을 확인했다. 자동 Reclaim 전체 성공은 미검증이며 목표 여유 60GiB에 도달했다고 기록하지 않았다.
