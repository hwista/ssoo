# 폐쇄형 플랫폼·조직·서비스 온보딩 기반 점검

> 2026-10-01 · 코드/스키마 및 로컬 DB 읽기 전용 점검 완료 · 제품 적용 미완료

공용 모델·API·화면 구현의 진행 상태와 미완료 항목은 [구현 대장](2026-10-01-onboarding-implementation.md)을 따른다. 아래 표는 구현 전 기준의 점검 결과다.

## 적용할 기준

사용자가 확정한 가장 바깥 경계는 **그룹사 등을 포함하는 하나의 폐쇄형 플랫폼**이다. 개별 법인·회사·부서·팀은 그 안의 조직이며, 서로 독립된 공개 SaaS 고객 테넌트를 전제하지 않는다. 문서·게시물의 소유자는 개인으로 유지하고, 공개 범위는 개인/조직/전체로 통일한다. 전체는 같은 플랫폼의 허용된 사용자 범위이므로 법인·회사 간에도 공개될 수 있다. 인터넷 공개나 모든 개인 자료의 자동 공개라는 의미는 아니다. PMS·CRM 업무 데이터는 해당 업무 조직에 귀속되고, 그 과정에서 생성된 문서도 개인 소유자를 기록하면서 업무 조직에 자동 공개한다. 퇴사·소속 변경과 데이터 보존을 분리한다.

관리자 생성·셀프 가입 모두 ID 생성 후 공용 온보딩에서 회사/조직 소속 또는 신규 생성을 신청하고 서비스 이용을 신청한다. 조직 소속과 서비스 이용 승인은 분리하며 해당 권한자 또는 플랫폼 관리자가 처리한다. Admin은 일반 조직 소속이 아니라 플랫폼 관리자 권한으로 진입한다. SNS·DMS 개인 이용도 승인된 플랫폼 구성원 범위 안에서 이뤄진다.

운영 형태 확인에 사용자는 하나의 플랫폼에서 여러 회사를 지원하는 경우도 고려하되, 그룹사 전체처럼 하나의 운영 울타리라고 답했다. 따라서 `회사 A → 회사 B`라는 이유만으로 전체 공개 자료를 차단하지 않는다. 플랫폼 참여 자격·서비스 이용 승인과 선택한 조직 범위를 집행하는 것이 핵심이다. 각 회사마다 독립 DB를 강제하거나 모든 테이블에 SaaS용 tenant 키를 추가하는 설계는 이번 기준에 포함하지 않는다. 폐쇄망·인프라 접근 통제의 실환경 검증은 이번 코드 점검 범위가 아니다.

## 결론

기존 인증·권한·공유 기능은 재사용할 수 있다. **현재 상태에 온보딩 화면만 붙여서는 승인한 회사/조직/서비스 범위를 일관되게 집행할 수 없다.** 계정 발급과 업무 이용 승인 사이의 공용 모델, 각 앱의 범위 검사, 검색과 생성 문서의 연결을 함께 완성해야 한다. 이 문서의 준비 여부는 새 정책 기준이며 기존 기능의 존재 자체를 부정하지 않는다.

## 구체적 확인 근거

### 공용·Admin·PMS·CRM

- [조직 모델](../../../../packages/database/prisma/schema.prisma)의 `Organization`은 회사/부서 등을 표현할 수 있지만 회사 소속 확인과 서비스 신청/이용권의 정본이 아니다. [조직 운영](../../../../apps/server/src/modules/common/access/organization-operations.service.ts)은 계층 CRUD이며 소속 신청 심사 기능이 아니다.
- [공용 권한 계산](../../../../apps/server/src/modules/common/access/access-foundation.service.ts)은 전역 역할과 유효 상설 조직의 권한을 합산한다. 하위 조직의 grant가 어느 조직·서비스·업무 객체에 유효한지 새 계약과 연결해야 한다. [서비스 이동 안내](../../../../packages/web-auth/src/service-access.ts)는 기존 domain snapshot을 읽을 뿐 승인된 앱 이용권을 저장하지 않는다.
- [PMS 조회/생성](../../../../apps/server/src/modules/pms/project/project.service.ts)은 소유 조직·담당자·참여자 범위가 있다. 생성 시 명시한 `ownerOrganizationId`를 반환하거나 담당자의 주 소속을 찾아 nullable로 저장한다. 공용 온보딩 승인과 연결한 회사·하위 조직 검증은 없다.
- [CRM 원장 조회](../../../../apps/server/src/modules/crm/contract/contract.service.ts)의 `listContracts`는 현재 사용자 조직을 인자로 받지 않는다. 영업기회·고객·계약 master에는 담당 사용자 정보가 있으나 소유/귀속 조직 키는 없다. 거래 고객사명이나 영업 공급자 프로필을 도입 회사 경계로 간주하지 않는다.

### DMS·SNS·업무 문서

- [DMS 문서 패널](../../../../apps/web/dms/src/components/pages/markdown/_components/DocumentPanel.tsx)은 공개 범위 변경 시 `{ visibility: { scope } }`를 전달한다. [관리 API](../../../../apps/server/src/modules/dms/access/access-request.service.ts)의 `updateDocumentVisibility`는 `self | organization`만 받고 조직 전환 시 대상 조직을 지정하지 않는다. [ACL](../../../../apps/server/src/modules/dms/access/document-acl.service.ts)의 `isVisibilityReadable`에는 조직 대상이 없으면 조직 소속 사용자에게 열람을 허용하는 호환 동작이 있다.
- DMS의 `approveReadRequest`는 신청자 user에 실제 grant를 저장하고 신청 상태를 승인으로 바꾼다. 현재는 **개별 권한을 추가하는 방식**으로, 공개 범위 자체를 자동 전환하지 않는다. 사용자 표현인 “개별 공유로 전환”을 구현할 때 기본 공개 범위 변경 여부를 이 동작과 구분해야 한다.
- [SNS 공개 처리](../../../../apps/server/src/modules/sns/access/access.service.ts)는 `public`을 별도 회사 조건 없이 허용 후보로 넣고, 조직 공개는 사용자의 주 소속 조직으로 고정한다. 이 public 동작 자체는 폐쇄형 플랫폼 전체 공개 방향과 맞으며 회사 간 차단을 추가할 근거로 삼지 않는다. 플랫폼 참여/서비스 승인 조건을 별도로 연결해야 한다. [게시물 작성 UI](../../../../apps/web/sns/src/components/pages/feed/ComposeBox.tsx)에 기존 팔로워 공개가 있다. 개인/조직/전체 통일 시 기존 게시물의 변환 기준을 정해 노출 확대나 임의 소실을 방지해야 한다.
- [CRM 계약 초안 생성](../../../../apps/server/src/modules/crm/contract/contract.service.ts)의 `saveDmsDocumentDraft` 경로와 [DMS 계약 산출 기록](../../../../apps/server/src/modules/dms/crm-contract-lifecycle/crm-contract-lifecycle.service.ts)의 `writeMarkdownArtifact`는 현재 사용자로 일반 파일 쓰기를 호출한다. [일반 파일 생성](../../../../apps/server/src/modules/dms/file/file-crud.service.ts)은 새 markdown에 개인 소유자와 `visibility: { scope: 'self' }`를 기본 설정한다. 해당 경로에는 원천 업무 조직을 전달해 조직 공개로 설정하는 처리가 없다. 조직명 문자열이 들어간 산출 경로도 그 자체로 ACL이 되지 않는다. 모든 PMS 산출물 생성 경로를 동적으로 검증한 결과는 아니므로 각 경로 목록화와 회귀가 추가로 필요하다.

### 검색·AI·알림과 회수

- [CRM 통합 검색 provider](../../../../apps/server/src/modules/crm/search/crm-common-search.provider.ts)는 `currentUser`를 사용하지 않고 원장을 조회해 `permissionState: readable`로 반환한다. 공용 검색 서비스가 provider에 전달하는 사용자 문맥을 새 회사/조직/서비스 범위와 함께 실제 필터에 사용해야 한다.
- [AI 검색](../../../../apps/server/src/modules/common/ai-index/ai-retrieval.service.ts)의 `aclPredicateSql`에 `access_scope_code = 'organization' AND user IS NOT NULL` 조건이 있다. 뒤의 조직 ID 일치 조건과 OR 관계여서 조직 범위만으로 대상 조직 일치를 강제한다고 볼 수 없다. 플랫폼 참여·대상 조직·서비스 승인·객체 권한 회수 후 재검사까지 연결할 대상이다. 실제 다른 조직의 제한 자료 접근을 HTTP로 재현한 결과는 아니다.
- [기존 DMS 공개 정본](../../../dms/explanation/domain/document-visibility-and-access-model.md)은 본문 비접근자의 검색 발견과 일부 요약/인용 표시를 허용한다. “개인” 자료의 제목·요약·AI 인용까지 숨길지, 권한 신청을 위한 발견 정보를 별도로 허용할지는 새 개인 공개 의미와 맞춰 명시해야 한다.
- [공용 알림](../../../../apps/server/src/modules/common/notification/notification.service.ts)은 수신자 사용자별로 분리된다. 회사/서비스 권한 회수 후 과거 알림 요약 노출과 링크 진입을 어떻게 처리할지 추가 검증한다. 기존 [세션 검증](../../../../apps/server/src/modules/common/auth/auth.service.ts)은 계정 활성/폐기를 확인하지만 아직 없는 서비스 이용권의 회수를 대신하지 않는다.

## 실행 데이터와 증거 수준

로컬 DB를 읽기 전용으로 집계했다. 활성 조직 13개가 모두 최상위이며 `org_type=company`는 0개다. 회사 유형이 0이라는 사실만으로 도입 회사가 없다고 단정하지는 않지만, 현재 자료가 회사→하위 조직 계층으로 정리돼 있다는 증거는 없다. 프로젝트 6개 모두 소유 조직이 있고, 활성 조직 공개 문서 34개는 대상 조직이 비어 있다. 증거는 `output/service-onboarding-review/20261001/database-summary.json`이다.

이번 점검은 현재 작업트리의 코드·스키마·화면 연결과 배포 DB의 읽기 전용 확인이다. 새 계정/회사 생성, 타인 계정 로그인, 권한 변경, 실제 권한 신청·승인, 외부 메일, 제품 수정·배포는 수행하지 않았다. 이전 로그인 smoke 또는 preflight 통과를 새 온보딩/회사 격리 통과로 집계하지 않는다. 작업 전 preflight는 통과했다.

## 구현 의존 순서

1. **공통 경계 확정:** 폐쇄형 플랫폼 참여 자격, 내부 회사·하위 조직 관계, 소속과 서비스 이용권, 승인 권한의 범위, 개별 공유와 개인 검색 노출의 의미를 계약으로 정한다. 플랫폼 전체 공개와 조직 한정 공개를 구분한다.
2. **기존 데이터 이전 설계:** 회사·조직 매핑, 미소속 계정, DMS 대상 조직 누락, SNS 팔로워 공개, CRM 귀속 조직과 검색 인덱스를 점검한다. 소유자를 조직으로 일괄 교체하지 않는다. 현재 사용자의 역할을 전역 삭제하지 않는다.
3. **서버와 각 앱의 접근 집행:** 플랫폼 참여/서비스 승인 조건과 PMS·CRM 조직 업무 범위, DMS·SNS 공개/개별 공유, 생성 문서 조직 문맥, 검색·AI·파일 접근을 연결한다. Admin 관리 권한과 일반 승인함 진입을 분리한다.
4. **공용 온보딩과 승인 운영 연결:** 신청·승인·부분 승인·반려·철회·재신청과 기존 사용자 전환을 실제 권한 저장/조회에 연결한다. 화면 설계는 앞 단계와 함께 진행할 수 있지만, 화면 완성만으로 출시하지 않는다.
5. **격리 환경에서 통합 검증 후 반영:** DB 복제본과 테스트 계정으로 아래 기준을 통과한 뒤 사용자 환경에 반영한다.
