# 소속·서비스 접근 관리의 기능별 화면 설계

> 작성: 2026-10-27 · 최종 확인: 2026-10-28 · 상태: 기존 로컬 배포 및 기능 검증 완료

## 문제와 결정

기존 작업은 대시보드에 운영 준비 카드를 추가하고 로그인 경계에서 조직 등록 안내, 개인 신청, 담당 승인, 권한 위임을 하나의 온보딩 화면으로 렌더했다. 시나리오를 화면 구조로 사용해 기존 관리 메뉴와 중복되고, 기능을 독립적으로 찾거나 다시 사용하는 경로가 불명확했다. 사용자가 이 작업의 제거와 기능 중심 재설계를 명시적으로 요청했다.

시나리오는 기존 기능을 잇는 검증 절차다. 제품에 단계별 운영 준비 페이지나 시나리오 전용 메뉴를 두지 않는다. 각 화면은 하나의 책임, 영구 주소, 메뉴 진입점, 재조회·오류 복구와 권한 경계를 가진다.

## 화면 책임과 메뉴

| 기능 | 메뉴 / 주소 | 사용자 | 책임 |
|---|---|---|---|
| 회사·팀 관리 | 플랫폼 관리 → 조직 관리 `/organizations` | 플랫폼 관리자 | 조직 생성·수정·비활성, 계층·구성원 수 조회 |
| 로그인 계정 관리 | 플랫폼 관리 → 사용자 관리 `/users` | 플랫폼 관리자 | 계정 생성·활성 상태·참여 상태·실제 승인 소속 조회 |
| 개인 소속 관리 | 내 업무 → 내 소속 `/my-organizations` | 로그인 사용자 | 현재 소속, 기존 조직 소속 신청, 새 조직 생성 신청, 해당 신청 내역·취소·재신청 |
| 개인 서비스 접근 | 내 업무 → 서비스 이용 `/my-services` | 로그인 사용자 | 조직별 이용권·역할, 서비스 신청, 해당 신청 내역·취소·재신청, 승인된 서비스 열기 |
| 신청 처리 | 내 업무 → 신청 승인 `/approvals` | 관리자 또는 유효한 위임 담당자 | 담당 범위의 신청 조회, 유형·상태 필터, 승인·반려·처리 내역 |
| 승인 권한 위임 | 플랫폼 관리 → 역할 & 권한 → 승인 권한 위임 `/roles?tab=approval-authorities` | 플랫폼 관리자 | 조직·서비스별 담당자 검색·적격성 확인·최대 역할 설정·위임·회수 |

개인 업무와 신청 승인은 Admin의 기존 플랫폼 셸/MDI에 등록한다. Admin 접근 전체를 관리자만 허용하던 클라이언트 경계를 기능별로 나누며, 관리 API의 서버 인가는 그대로 유지한다. 다른 네 앱의 공용 사용자 메뉴는 이 정본 주소로 이동한다. 동일 기능을 다섯 앱에 복제하지 않는다.

서비스 이용 미승인 상태에서도 개인 신청 화면에는 접근할 수 있어야 한다. 서비스 접근 경계는 이용 불가 이유, 개인 기능으로 이동, 승인된 서비스 이동, 재조회·로그아웃만 제공한다. 신청/승인 폼을 렌더하지 않는다. Admin의 비관리자 홈은 내 소속을 표시하며 관리자 전용 메뉴·새 사용자 버튼·저장된 관리 탭을 노출하거나 마운트하지 않는다.

최초 관리자 설정 `/setup`은 계정이 없는 설치 상태에서만 사용하는 독립 기능으로 유지한다. 기존 계정이 있는 로컬 DB를 초기화하거나 별도 미리보기 DB/포트를 추가하지 않는다.

## 시나리오 S01의 메뉴 순서

1. 관리자: 조직 관리에서 회사와 개발팀 등록.
2. 관리자: 사용자 관리에서 담당자와 직원 계정 생성. 계정 생성과 소속/서비스 승인을 구분.
3. 담당자: 내 소속에서 개발팀 소속 신청.
4. 관리자: 신청 승인에서 담당자 소속 승인.
5. 관리자: 역할 & 권한의 승인 권한 위임에서 개발팀 소속 승인, PMS 승인, DMS 승인을 각각 위임.
6. 직원: 내 소속에서 개발팀 소속 신청.
7. 담당자: 신청 승인에서 직원 소속 승인.
8. 직원: 서비스 이용에서 PMS·DMS 신청.
9. 담당자: 신청 승인에서 서비스별 일반 사용자 역할 승인.
10. 직원: 서비스 이용에서 승인 상태 확인 후 해당 앱 열기.

각 화면은 앞 단계를 수행하지 않고 직접 주소/메뉴로 열어도 사용 가능한 상태와 부족한 조건을 설명해야 한다. 회사에 위임한 권한이 하위 팀으로 전파되지 않으며, 본인 신청 승인 및 최대 역할 초과는 서버에서 차단한다.

## 제거와 보존 범위

- 제거: 대시보드 운영 준비 카드, `?onboarding=1` 통합 화면, 단계 안내, 조직/사용자 화면에서 통합 화면으로 돌아가는 링크, 공용 사용자 메뉴의 혼합된 신청·승인 항목.
- 기능별 화면으로 이동: 신청·취소·반려 후 재신청, 승인·반려, 위임·회수, 조회 실패 복구, 적격 담당자 검색.
- 보존: 기존 조직/계정/역할/예외/감사/인증 관리, 계정 복구, 최초 설정, 소속 전체 경로, 계정 활성과 참여 상태 구분, 서버 인가와 감사 기록.
- 데이터: 기존 DB를 유지한다. 브라우저 검증용 레코드는 구분 가능한 이름으로 생성하고 검증 후 제거 및 기존 데이터 동등성을 확인한다.

## 완료 증거

- [x] 대시보드 및 제품 코드에 시나리오 단계/통합 온보딩 진입점이 없음.
- [x] 각 기능을 메뉴와 직접 주소로 독립 접근; 새로고침·MDI 탭 재선택·권한 변경 시 일관됨.
- [x] 일반 직원에게 관리 메뉴/관리 컴포넌트/API 요청이 노출되지 않음.
- [x] S01을 관리자·담당자·직원의 실제 로그인과 메뉴 이동으로 끝까지 수행.
- [x] 승인 대기/반려/취소/재신청, 위임 회수, 본인 승인 금지, 타 조직/최대 역할 경계 검증.
- [x] 데스크톱 1440×1000·모바일 390×844에서 기능별 화면 확인; 관련 API/proxy/console/runtime 오류 없음.
- [x] 사전 검사, 규칙 동기화, 문서 검사, 관련 테스트, 서버+5앱 플랫폼 검사 통과.
- [x] 기본 로컬 포트 3000~3004/4000 갱신 및 새 코드 브라우저 검증. 추가 환경/검증 데이터 정리.
- [x] 사용 안내를 메뉴별 책임과 S01의 메뉴 이동 순서로 교체하고 이전 완료 주장을 현재 검증 결과로 정정.

## 실제 검증 기록

- 기존 로컬 Docker의 Admin 3000, CRM 3001, PMS 3002, DMS 3003, SNS 3004, 서버 4000, PostgreSQL 5432를 사용했다. 추가 포트·DB를 만들지 않았다.
- 관리자 UI에서 회사·팀과 담당자·직원 계정을 만들고, 세 브라우저 세션의 실제 로그인과 메뉴 이동으로 S01을 수행했다. 직원의 PMS 업무 브리핑과 DMS 문서 업무 허브 진입, 공용 사용자 메뉴로 Admin의 서비스 이용 화면에 돌아오는 동작까지 확인했다.
- 미승인 CRM·SNS의 접근 안내에서 내 소속·서비스 이용으로 이동했고, 일반 직원의 `/users` 직접 접근·새로고침에서 관리 컴포넌트/API 요청과 관리 탭 노출이 없었다.
- 신청 취소·반려 사유·재신청, 승인/서비스 유형별 처리 내역, 위임 검색의 미소속 사용자 선택 차단, 직접 주소·새로고침·모바일 메뉴·MDI 재선택을 검증했다. 승인함 503 오류를 주입한 뒤 ‘다시 조회’ 복구를 확인했다.
- 실브라우저에서 소속 승인 전 알림 API의 403 오류를 발견해 Admin 알림의 마운트를 참여 승인 이후로 제한했다. 새 직원의 첫 로그인 재검증에서 관리/알림 API 호출과 관련 오류가 0건이었다.
- 실제 API의 회수 후 승인 시험에서 빈 `OR` 범위가 신청 ID와 결합될 때 처리 권한을 제한하지 못하는 결함을 발견했다. 위임이 없으면 빈 ID 집합으로 명시적으로 거부하도록 수정하고 결정 경로의 회귀 테스트를 추가했다. 수정된 실제 서버에서 동일한 요청이 403으로 차단되고 승인함이 빈 결과를 반환함을 재검증했다. 실패 재현으로 만들어진 하위 조직까지 생성 ID를 확인해 정리했다.
- 장시간 검증 대기 중 세션 만료가 발생한 경우 정상 로그인/세션 복구 후 다시 실행했다. 의도적으로 주입한 오류·권한 거부와 수정 전 실패는 성공 증거로 계산하지 않는다.
- 증거: `output/playwright/functional-access-20261027/`의 화면 캡처, `api-*.json`, `revocation-before.json`, `fixtures.json`, `data-before.json` 및 최종 비교 결과. 스크린샷은 1440×1000과 390×844에서 실제 표시를 확인했다.

## 최종 판정과 보존 범위

- `codex:platform-guard`: 서버와 5개 웹 앱 production build, 서버 102묶음·777테스트 통과. `codex:preflight`, 규칙 동기화, 변경 파일 52개 패턴 검사, Admin/server 변경 범위 lint, 문서 검사 통과.
- 실제 API 경계 검사: 승인 전 15건, 승인 결과 10건, 위임 회수 후 8건 통과. 최종 세 브라우저 확인은 총 132개 API 응답에서 오류/실패 0건이었다. 예상된 거부와 오류 주입은 별도 기록했다.
- 검증 계정 2개, 조직 3개(실패 재현에서 생성된 하위 조직 포함), 신청 11개, 서비스 이용권 2개, 승인 위임 3개 및 관련 소속·인증·이력을 정확한 ID로 정리했다. 계정 비밀번호를 재설정하거나 기존 DB를 초기화하지 않았다.
- 13개 비교 대상 중 DMS 문서를 제외한 12개 업무 테이블과 로그인 자격증명 지문은 작업 전과 일치한다. DMS 문서는 159건을 유지했고, 작업 전 이력의 지문 `7604740b145a47c8e8e92e11d305ea94`가 최초 기록과 일치했다. 86건의 `last_scanned_at`, `last_reconciled_at`, `updated_at`, `updated_by`, `transaction_id`만 조회 동기화로 변경됐으며, 이 감사 필드를 제외한 문서 내용·권한·경로·버전 지문은 전후 동일하다. 감사 갱신을 숨기려고 되돌리지 않았다.
- 기본 로컬 포트와 원래 DB 볼륨을 유지한다. 첫 이미지 빌드의 다운로드 시간 초과는 캐시를 재사용해 재시도했으며 최종 배포 상태는 정상이다. 제품 메뉴 검증용 브라우저는 모두 종료했다. 검증 후 호스트의 5앱 `.next`와 `.turbo` 산출물 3,760,390,039 bytes, Docker 미사용 빌드 캐시 5.882GB를 정리했다. 실행/복구 이미지와 DB 볼륨은 유지하며 이 수치를 Windows C: 물리 반환량으로 주장하지 않는다.
- 이 완료 판정은 S01의 조직·계정·소속·서비스·승인 업무에 대한 것이다. PMS 프로젝트 수행이나 DMS 문서 작성 등 후속 업무 시나리오 전체를 검증했다는 뜻은 아니다.
