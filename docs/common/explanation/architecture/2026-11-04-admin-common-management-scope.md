# Admin 플랫폼 공통 관리 적용 범위

> 기준일: 2026-11-04
> 상태: 사용자 지정 범위를 반영한 코드 기반 검토안. 기능·메뉴 구현 완료 판정 아님.

구체적인 프로그램별 관리 대상·처리 기능·현재 구현·진입 위치와 AC01~AC15의 사용 순서는 [Admin 공통 관리 프로그램 목록](2026-11-04-admin-program-catalog.md)을 참조한다.

## 1. 이번 검토의 경계

사용자 지시에 따라 첫 적용 대상은 **Admin 앱의 플랫폼 공통 관리**다. 도메인 특화 관리는 각 애플리케이션의 설정 영역이 소유한다. [36개 전체 목록](2026-11-03-master-data-program-inventory.md)은 조사 자료로 유지하고, 현재 적용 순서는 이 문서를 따른다.

Admin의 책임은 플랫폼에 참여하는 조직과 사용자, 소속 관계, 앱 이용 자격, 공통 권한·인증 정책과 그 운영 증거다. 여러 앱이 참조하거나 공통 DB에 저장된다는 사실만으로 관리 책임이 Admin으로 옮겨지는 것은 아니다.

공통 관리에서 바꾼 상태가 5개 앱에 적용되는지는 이번 범위의 검증 대상이다. 계약·프로젝트·문서·게시물의 업무 규칙과 개별 객체 관리 기능은 각 앱이 소유한다. 이번 작업은 범위와 검증 기준을 정리하며 기존 UI를 변경하지 않는다.

## 2. Admin이 담당할 관리 기능

아래 9개는 기능을 검토하기 위한 묶음이다. 메뉴 개수나 새 화면 개수는 아니다. 기존 화면·상세 탭과 공통 데이터 변경 로직을 기준으로 프로그램을 설계한다.

| ID | 공통 관리 영역 | 관리 대상·필요 작업 | 현재 구현과 우선 검토 사항 | 기존 목록 |
|---|---|---|---|---|
| A01 | 회사·조직·소속 관리 | 플랫폼 참여 조직 계층, 구성원 배치, 주 소속·겸직, 이동·종료, 조직 중지·복구 | `/organizations`에서 조직 CRUD·계층·비활성화 보호 구현. 소속은 신청·승인 중심이며 일반 배치·이동·종료 프로그램 보완 필요 | P01/P03 |
| A02 | 사용자·계정 관리 | 계정 등록·정보 변경, 참여 상태, 이용 중지·재활성화, 잠금 해제·세션 회수·복구 | `/users`와 인증 운영 API 존재. 계정 중지·플랫폼 참여 상태·소속 종료·이용권 회수가 어떤 작업에서 함께 처리되는지 명세 필요 | P02 및 P08의 참여 상태 |
| A03 | 애플리케이션 이용 관리 | 앱 목록·접속 정보, 사용자×조직×앱의 이용권, 서비스 역할·기간·회수 | 앱 목록은 코드 고정. 신청·승인·본인 조회 존재. 이용권 회수 API의 Admin UI 연결, 운영자 조회·역할/기간 변경 경로 부족. Admin 운영 권한과 네 업무 앱 이용권을 구분 | P07/P08 |
| A04 | 공통 역할·권한 관리 | 공통 역할별 기능 권한, 관리 범위, 조직별 권한·사용자 예외, 실제 적용 권한 진단 | `/roles`에서 역할 권한 편집·명세·조회·예외 조회 존재. 임의 역할 CRUD와 조직 권한/예외 편집은 완성된 일반 관리 기능으로 볼 수 없음. 운영자가 수정할 정책 범위부터 확정 | P04/P05/P06 |
| A05 | 공통 신청·승인 운영 | 조직 생성·소속·앱 이용 신청, 담당자 위임, 승인·반려·취소·처리 이력 | `/approvals`, `/roles`의 승인 위임, `/onboarding` 존재. 가입 요청은 별도 인증 API. 담당자 부재·회수·재지정, 오래된 신청의 처리 조건을 검토 | P09 및 공통 신청 기록 |
| A06 | 플랫폼 공통 기준정보 | 공통 코드·표시명·분류·활성 상태와 참조 관계 | `/codes` 존재. 코드별 소유 책임을 명확히 하며 CRM/PMS 전용 코드의 의미·검증·특화 편집은 각 앱 소유 | P11의 공통 부분 |
| A07 | 인증·공통 연결 정책 | 공통 로그인·외부 인증 설정, 가입 허용 정책, 계정 복구·메일 전송 운영 | `/auth`에 Entra 정책과 복구 메일 운영 구현. MFA·외부 계정 연결 해제·M365/Teams 전반은 구현된 것으로 간주하지 않음. 실제 사용하는 연결부터 적용 | P10 |
| A08 | 감사·공통 운영 진단 | 공통 변경 이력, 변경자·대상·사유, 접근 거부 원인, 공통 처리 실패 조회·재처리 | `/roles` 감사/권한 조회와 `/auth` 메일 운영이 분산 존재. 소속·이용권·위임까지 필요한 이력이 조회 가능한지 확인. 모든 도메인 작업의 통합 복구 화면을 의미하지 않음 | 공통 이력·실행 데이터 |
| A09 | 공통 AI 운영 | 공유 제공자 준비 상태, 등록 소스, 공통 색인 작업·실행 상태 | `/ai-operations`는 기존 운영 기능. 제공자·모델·프롬프트·에이전트 종합 설정은 향후 요구로 구분. 문서 검색·분석 세부 정책은 DMS 설정 소유 | P13의 공통 부분 |

### 경계가 섞이기 쉬운 항목

| 대상 | Admin의 책임 | 각 앱의 책임 |
|---|---|---|
| 회사·조직과 거래처 | 플랫폼 참여 주체·조직 계층·구성원 | CRM 고객·견적 공급자 정보, PMS 수행 고객·사업장. 데이터 연결 필요성은 유지하되 이번에 거래처 통합 관리로 확대하지 않음 |
| 권한 | 플랫폼 관리자, 서비스 입장 자격, 공통 역할/권한 배정과 진단 | 계약 승인자, 프로젝트 구성원·역할, 문서 공유·소유권, 게시물 접근 규칙 |
| 승인 | 가입·소속·조직 생성·앱 이용 등 공통 요청과 위임 | 계약·산출물·문서·게시물별 승인. 같은 승인 명칭만으로 처리 규칙을 합치지 않음 |
| 코드 | 공통 저장·이력 기반과 플랫폼 공통 코드 관리 | 도메인 코드 의미·허용값·전환 규칙·관리 UI. 현재 공용 편집 화면의 노출 조정은 별도 변경 대상으로 기록 |
| 앱·메뉴 | 앱 식별·접속·이용 정책, Admin 자체 메뉴 | 앱 내부 메뉴 배치·기능 설정. 기존 P12의 PMS 메뉴/역할 메뉴 관리를 Admin으로 옮기지 않음 |
| 개인정보·프로필 | 계정 식별·상태·운영자 복구 | SNS가 소유한 프로필·스킬·경력과 공용 본인 설정 화면 |
| 연계·AI | 공유 인증·제공자·공통 실행 기반 | CRM 인계·회계 정책, DMS 저장소·템플릿·검색 정책 등 도메인 설정 |
| 계정 중지·퇴사 | 공통 접근 차단, 소속·이용권·위임의 후속 처리 상태와 이력 | 진행 중 계약·프로젝트·문서의 담당자·소유자 이전. Admin은 필요한 경우 해당 앱의 처리 경로를 안내 |

앱·서비스의 기준정보는 고정 5앱 운영에서 코드 관리 방식도 가능하다. 운영자에게 변경이 필요한 값이 정해지기 전에 동적 앱/메뉴 마스터와 범용 화면 생성기를 도입하지 않는다. 플랫폼 공통 권한 편집이 도메인의 실제 권한 검사 코드를 임의로 생성하거나 바꾸는 구조도 아니다.

공통 검증의 행위자는 플랫폼 관리자, 위임받은 조직/서비스 담당자, 일반 사용자, 중지/권한 없는 사용자로 나눈다. 같은 역할이라도 조직 범위가 다른 경우를 포함한다. 도메인 사용자 역할을 새로 정의하는 것은 이번 표의 목적이 아니다.

## 4. 적용 전에 먼저 구체화할 공백

1. **소속 관계의 관리:** 현재 조직 중지는 활성 구성원을 먼저 이동·비활성화하도록 요구한다. 그 선행 작업을 Admin에서 수행할 운영 프로그램이 필요하다. 신청 승인만으로 대체되지 않는다.
2. **이용권의 관리:** 기존 회수 API를 포함해 운영자가 대상 사용자·조직·앱의 이용권을 찾고 변경·회수하는 경로를 정한다. 서비스 이용 본인 화면의 목적과 구분한다.
3. **상태 변경의 영향:** 현재 사용자 중지는 `User.isActive`, 인증 계정 상태, 세션을 변경한다. 일반 승인 소속·이용권·위임의 종료 정책까지 모두 처리했다고 판정하지 않는다. 일시 중지와 퇴사를 구분하고 재활성화 시 자동 복원 여부를 명세한다.
4. **공통 역할·관리 범위:** 사용자 기본 역할, 앱 이용권 역할, 승인 가능한 최대 역할, 조직 권한·사용자 예외의 우선순위와 편집 책임을 확정한다.
5. **운영 이력:** 위 작업을 누가 어떤 범위에서 처리했는지 사용자용 조회 경로까지 확인한다. 이력 테이블만으로 운영 추적이 완료됐다고 보지 않는다.

위 항목을 먼저 설계하고 기존 A06/A07/A09 기능은 해당 공통 운영 시나리오로 검증한다. AI 정책 확장이나 전사 고객 통합을 소속·이용권 운영 완성의 선행조건으로 두지 않는다.

## 5. 화면 구성과 현재 세 메뉴

현재 Admin의 사용자 관리·조직 관리·역할 & 권한·공통코드·인증 정책·AI 운영을 프로그램 배치의 출발점으로 삼는다. 소속 관리는 조직/사용자 상세에서 같은 관계를 보게 하고, 이용권 관리는 사용자별·앱별 관점을 제공하는 방향을 검토한다. 신청 내역·승인 처리는 같은 원본 관계에 변경을 요청하는 기능으로 연결한다. 이 배치 방향은 아직 최종 메뉴 확정이나 UI 변경을 뜻하지 않는다.

`내 소속`, `서비스 이용`, `신청 승인`은 공통 관계를 사용하는 본인/담당자용 기능이다. Admin 운영자의 전체 관계 조회·변경·종료 기능을 대신하지 않는다. 이 세 진입점의 유지·배치는 공통 관리 프로그램의 대상과 작업을 확정한 뒤 판단한다.

완료 조건은 메뉴 수가 아니라 위 시나리오별로 **담당자 → 기존/보완 프로그램 → 변경 데이터 → 적용 범위 → 실패 복구 → 확인 증거**가 연결되는 것이다.
