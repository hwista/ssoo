# 공용 온보딩 구현 대장

> 현재 상태: 2026-10-06 로컬 Docker 배포·기존 DB 이전·실사용 인계 완료 · 아래 단계별 기록은 당시 이력

최신 배포 기준·보존 데이터·검증과 테스트 순서는 [로컬 배포 완료 기록](2026-10-02-onboarding-wsl-resume.md#로컬-docker-배포-완료--2026-10-06)을 따른다. 이후 작업트리 변경까지 배포됐다는 뜻은 아니다.


정책 정본은 [서비스 기반 점검](2026-10-01-service-onboarding-readiness.md)이다. 그룹사 등을 포함한 폐쇄형 플랫폼을 경계로 삼고 회사별 공개 SaaS 격리를 추가하지 않는다. 문서·게시물의 개인 소유자는 유지한다.

사용자가 과거 업무 자료는 에이전트가 생성한 폐기 가능한 자료이며 사용자 작성·테스트 데이터가 아니라고 정정하고 클렌징을 승인했다. 과거 자료의 신규 계약 전환은 온보딩 잔여 과제에서 제외한다. 로컬 CRM/PMS 데모 업무 자료의 실제 삭제 및 계정·조직·기준정보 보존 결과는 [재개 기록의 클렌징 결과](2026-10-02-onboarding-wsl-resume.md#2026-10-02-승인된-과거-자료-클렌징)를 따른다. 온보딩 코드 배포와 데이터 정리는 별개다.

## 실행 단계

| 단계 | 상태 | 범위 |
|---|---|---|
| 1 | 구현·격리 검증 완료 | 플랫폼 참여 상태, 소속/신규 조직/서비스 요청, 앱 이용권, 승인 위임, 이력과 이전 검증 |
| 2 | 진행 중: 앱 진입·검색/알림 승인, PMS·CRM 기본 원장과 CRM 계획/원가/보고/운영·PMS 인계 연결; 문서·전체 통합 잔여 | 앱·통합 검색·AI·파일 접근과 조직 업무 범위 연결 |
| 3 | 구현·정적/단위 검증 진행, DB·브라우저 검증 대기 | DMS/SNS 공유 정렬, 업무 생성 문서의 개인 소유·업무 조직 공개 |
| 4 | 공용 화면·Admin/SNS/PMS/CRM 기본 폼 브라우저 검증, 전체 통합 잔여 | 공용 온보딩/승인함, 기존 사용자 전환, 실제 브라우저·DB 격리 회귀 |

## 구현 계약

- 기존 사용자의 참여/앱 접근은 migration 시점의 근거와 역할을 기록해 보존한다. 새 계정은 pending이며 관리자 생성과 외부 가입 승인 모두 공용 온보딩으로 진입한다. 이력 없는 누락 행을 자동 기존 사용자로 간주하지 않는다.
- 조직 관계는 승인된 소속의 정본으로 재사용한다. 신청 정보만으로 관계/조직을 활성 생성하지 않는다. 조직 소속 승인과 서비스 이용 승인은 별도 요청이다.
- 앱 이용권은 사용자·서비스·조직 범위·역할·승인 근거를 기록한다. 신규 일반 이용권은 승인된 소속을 전제로 하며 다른 회사라도 같은 플랫폼의 전체 공개를 볼 수 있다.
- 조직/서비스 승인 위임은 시스템 관리자와 구분한다. 요청자 본인은 자기 요청을 승인하지 못한다. 시스템 관리자의 초기 설정과 기존 관리 계정 보존은 일반 가입 경로와 분리한다.
- 요청 결정, 소속/이용권 반영, 감사 이력을 한 트랜잭션으로 처리한다. 중복·동시 결정과 소속/위임 회수를 검증한다. 기존 조직 관리에서 관계를 먼저 만들었더라도 pending 계정은 공용 소속 승인을 거치며, 그 관계 때문에 승인 신청이 막히거나 중복 소속 행이 생기지 않는다.
- 실제 사용 중인 Docker DB에 새 migration을 먼저 적용하지 않는다. 백업 복제본 및 새 격리 DB에서 이전·앱/검색·브라우저 검증을 진행한다.

## 현재 구현과 검증

- 신규 `PlatformEnrollment`, `OnboardingRequest`, `ServiceGrant`, `ApprovalAuthority`와 각 history/trigger를 추가했다. 기존 사용자 migration은 기존 action/object policy를 유지하는 compatibility admission을 기록한다. 서비스 이용권 자체가 새 세부 권한을 무조건 부여하지 않는다.
- 관리자 생성·외부 가입 승인 경로가 pending 참여 상태를 생성한다. 새 사용자에게 부서/회사 입력만으로 조직을 만들거나 연결하던 legacy bridge는 적용하지 않는다. 셀프 가입 API의 미구현 상태를 이번 작업으로 활성화하지 않는다.
- 신청 유형은 소속, 신규 조직, 서비스이고 pending/approved/rejected/cancelled 상태를 갖는다. 승인 위임은 조직/서비스와 조직 범위/최대 역할을 저장한다. 자기 신청 승인, 담당 범위 밖 결정, 소속 전 서비스 승인, 중복 신청/동시 결정은 서버에서 거부한다.
- 승인·관계·이용권·감사 이력은 Serializable transaction으로 처리한다. 조직 생성은 승인 때 수행한다. 소속 회수·위임 회수는 현재 조회에 반영하며 새 사용자의 서비스 역할을 계정 기본 역할과 분리한다.
- 서버 전역 admission guard, action/object permission, PMS 역할/메뉴, 공용 검색 provider 선택에 참여/서비스 승인을 연결했다. AI retrieval은 최신 조직과 원본 adapter의 현재 읽기 권한을 재확인한다. 조직 범위라는 이유만으로 모든 로그인 사용자를 통과시키던 AI 후보 조건을 제거했다.
- `SharedOnboardingBoundary`를 5앱 providers에 연결했다. 승인되지 않은 앱 진입 시 공용 화면을 표시한다. 기존 앱의 사용자 메뉴에서 `소속·서비스 신청 및 승인`으로 다시 진입할 수 있다. 화면은 `/?onboarding=1`이며 담당 승인함과 플랫폼 관리자의 승인 위임을 함께 제공한다.
- PMS 신규 등록은 승인된 업무 조직을 선택하고 서버 transaction에서 검증한다. 담당자 변경만으로 업무 조직을 바꾸지 않으며 새 자료의 담당자 기본값은 생성자다. 신규 이용권의 프로젝트 목록·상세·AI·공용 검색에는 업무 조직별 역할을 적용한다. 기존 migration/bootstrap 이용권은 종전 객체 정책을 유지한다.
- CRM 영업기회·고객·계약과 history에 `ownerOrganizationId`를 추가했다. 기존 행은 NULL 그대로 보존한다. 신규 생성은 승인된 CRM 쓰기 조직을 검증하고 담당자 변경은 조직을 바꾸지 않는다. 영업기회 차수와 원천이 있는 신규 계약은 원천 조직을 유지한다. 일반 수정에서 연결 자료를 다른 조직으로 이전하지 않는다.
- CRM 기본 목록/요약·대시보드·계약대비실적, 영업기회/고객 상세·검색·AI 원본 검사, 계약 상세 하위 API와 계약 승인함에 현재 조직 범위를 적용했다. 다른 조직의 manager 이용권이 viewer 조직의 수정 권한으로 확장되지 않으며, 회수 후 담당자 일치로 우회하지 않는다. 고객/활동의 원천 영업기회 연결도 같은 업무 조직으로 제한한다.
- CRM 세 기본 입력 화면은 같은 업무 조직 선택 컴포넌트를 사용한다. 조직 조회 실패는 공용 오류와 재시도를 제공한다. 조직이 하나면 선택을 채우고 복수 조직은 직접 선택한다. 과거 에이전트 생성 자료는 클렌징 대상이며 신규 계약으로 이관하지 않는다.
- 알림 목록·미확인 건수·읽음/안읽음 응답과 이미 열린 SSE 전달은 현재 승인 앱으로 제한한다. 회수 후 조회와 열린 스트림의 도메인 이벤트 전달 차단을 단위 검증했다. CRM/PMS 공용 검색은 결과의 제목·요약을 반환하기 전 원본 객체 권한을 재검사한다.
- 오류는 `SsooErrorNotice`/`SsooErrorPage`를 사용한다. 재시도·로그아웃을 유지하고, 503 주입 후 같은 화면으로 복구하는 브라우저 검증을 수행했다.

## 다음 단계와 적용 조건

아래는 초기 단계의 잔여 목록이다. 실제 통합 검증은 문서 하단의 2026-10-02 결과로 갱신됐고, 과거 자료 전환은 사용자 정정에 따라 제외했다. Docker 코드 배포는 별도다.

1. 기존 PMS·CRM 업무 자료는 에이전트 생성 자료이며 사용자가 클렌징을 승인했다. 보존을 요구했다는 기존 기록은 잘못된 해석이었다. 과거 조직 추정·일괄 재배정은 제외하고 신규/명시적 변경부터 승인된 업무 조직을 검증한다.
2. 조직 미지정 과거 영업기회의 신규 계약 전환은 요구 범위에서 제외한다. CRM 계획·원가·보고 집계와 저장본, 운영 진단/시도 이력/재시도, CRM→PMS 계약 인계에는 이번 후속에서 조직 문맥을 연결했다. PMS의 신규 프로젝트 생성 경로는 `ProjectService.create`이며 CRM 인계는 기존 프로젝트에 계약 스냅샷을 반영하는 경로다.
3. DMS 3범위 API/UI·승인 조직 선택과 업무 생성 문서의 개인 소유·출처 조직 공개를 구현했다. 조직 미지정 과거 자료의 실제 이전은 수행하지 않았으며 새 격리 DB·브라우저 검증이 남아 있다.
4. SNS 개별 공유 신청/승인/회수와 DMS WebSocket 전달 시 현재 권한 재검사를 구현했다. 문서·게시물 객체 권한 기준 공용 알림 재검사도 아래 후속에서 구현했다. 실제 DB·두 계정 브라우저 회귀는 남아 있다. 서비스 이용권 기준 알림/SSE 차단은 이전 단계에서 구현했다.
5. 위 도메인 변경을 합친 5앱 전체 수용 검증 및 실제 데이터 백업 복제 리허설 후 Docker 반영.

브라우저 증거는 `output/playwright/onboarding-20261001/`, 실행 로그는 이번 세션의 `/tmp/ssoo-onboarding-*.log`에 있다. 개발 서버의 CSP report-only 안내와 계정 전환 시 401, 의도적으로 주입한 503을 실제 오류 없이 통과한 것으로 세지 않는다. 초기 dev 컴파일/전환 시 script 오류와 HMR hook-order 경고가 있었고, 안정된 소스에서 Admin 진입/새로고침 및 PMS 등록/모바일 새로고침을 다시 측정해 API/pageerror 0을 확인했다. 세션 복원 전 온보딩 조회의 401은 accessToken 준비 상태를 조회 조건에 포함해 수정했다. PMS 최초 모바일 캡처는 반응형 상태 갱신 전 촬영되어 최종 증거에서 제외하며 `pms-organization-mobile-final.png`를 사용한다. 최종 브라우저 판정은 `final-checks.json`에 구분 기록한다.

첫 단계의 브라우저용 격리 DB와 검증 서버는 정리했다. CRM 후속 검증의 정리 결과는 후속 검증 항목에 기록한다. 기본 Docker/실사용 DB에는 변경을 적용하지 않았다.

## 2026-10-02 공용 알림 객체 권한 후속

- DMS/SNS 알림 목록·읽음/안읽음 응답 및 열린 SSE 전달에서 현재 원본 열람 권한을 재검사한다. DMS는 현재 DB 경로·메타데이터·서비스 권한·조직/개별 ACL을, SNS는 기존 게시물 읽기 정책과 현재 서비스 권한을 사용한다. 삭제·만료·회수된 대상이나 확인할 수 없는 객체는 제목/본문/참조/행위자/원문 이동 정보를 반환하지 않는다. DB 장애를 권한 거절로 숨기지 않고 기존 공용 오류 경로로 전달한다.
- 알림 자체를 삭제하지 않는다. 수신자의 읽음 상태·건수·생성 시각과 승인/회수 같은 고정 상태는 유지하며, DMS 권한 상태는 원문 경로 없는 권한 신청 설정으로 이동할 수 있다. 현재 열람 가능한 대상의 기존 알림 동작은 유지한다. SNS legacy 읽음 동기화 키는 알림 ID만 포함하는 형식에 한해 보존한다.
- 읽을 수 없는 도메인 이벤트는 원문 payload를 비우고 갱신 신호만 전달한다. SNS 공유 결정은 commit 이후 변경 이벤트를 발행한다. 공용 알림 클라이언트는 권한 변경 신호를 받으면 해당 앱의 이전 내용을 비운 뒤 재조회하여, 조회 실패가 오래된 원문 노출을 유지하지 않게 한다. SNS 공유 패널은 공유/공개 범위 변경에 재조회하고 늦게 도착한 이전 응답을 무시한다. 이미 읽은 데이터를 원격 삭제하거나 만료 순간의 즉시 화면 삭제를 보장하지는 않는다.
- 검증: 신규 원본 정책과 공용 응답/SSE, SNS 공유 결정을 포함한 관련 4 suites/22 tests 통과. 원문 허용/차단, 현재 조직·grant 만료·서비스 회수·삭제, 상태/읽음 이력 유지, 조회·변경 응답·대기 중 SSE의 재검사 및 DB 실패 전파를 검사했다. 최초 재검증 명령의 spec 경로 오기는 수정 후 재실행했으며 제품 실패로 세지 않는다.
- 브라우저 검증은 실제 공용 React hook과 SNS 공유 패널에 모의 API/EventSource를 연결했다. 권한 변경 뒤 조회 실패 시 이전 내용 제거, 다른 앱 알림·건수 유지, 재조회 복구, payload 없는 변경 신호, 늦은 승인 응답 무시를 확인했다. 이 증거는 실제 DB·두 계정 승인/회수·실제 SSE 전송 검증을 대신하지 않는다. 증거는 `output/playwright/notification-scope-20261002/`, 실행 로그는 `/tmp/ssoo-notification-scope-*.log`에 둔다.
- 환경 복구·Docker 배포는 별도 세션 범위다. 이 세션에서는 Docker/WSL 재시작이나 DB 복구를 수행하지 않았다. 남은 실환경 검증은 앞 절의 baseline/restore·공유 fixture·두 계정 브라우저 순서를 따른다.

## 2026-10-02 복구 후 실제 DB·공유 통합 검증

사용자의 “계속 진행하자” 요청으로 재개했다. 이 절은 앞의 DB 연결 장애로 인한 검증 대기 기록을 갱신한다. 기존 Docker 앱이나 업무 DB를 교체하지 않고 일회용 DB와 별도 API/DMS/SNS 프로세스를 사용했다.

- launch baseline과 populated restore가 19 migrations/90 triggers/schema drift 0으로 통과했고 두 baseline DB의 삭제를 확인했다. 온보딩 fixture에 연결된 CRM 기본 원장·계획/원가/보고/운영·PMS 인계·DMS/SNS 공유 시나리오도 통과했다. 최초 fixture의 DMS 사용자 ID 타입 불일치는 실제 토큰과 같은 문자열로 수정 후 재실행했다.
- SNS 두 계정의 신청→소유자 승인→열람→회수와 390px 모바일 화면을 실제 API로 확인했다. 게시물과 공유 패널의 React key가 같아 회수 뒤 이전 카드가 남을 수 있던 문제를 구분된 key로 수정하고 새 진입부터 다시 검증했다. 공용 세션 복구 화면의 children도 React Children API로 정규화했다.
- DMS에서 실제 파일 생성, 두 계정 재신청·승인·열람, 소유자의 수정 권한 전환·회수를 확인했다. 검색이 회수/만료된 grant를 계속 승인으로 표시하던 결함을 수정하고 서버 회귀 5개 및 실제 revoked/expired 응답을 확인했다. 요청 창은 서버의 현재 신청 상태를 조회하고 변경 이벤트에서 임시 상태를 비우며, 조회 실패 안내·메모 보존·다시 시도를 제공한다.
- 모바일 권한 관리에서 공용 화면 틀이 최초 로딩 상태일 때 너비 측정 ref를 연결하지 못하는 결함을 발견했다. 상태 화면과 본문이 전환될 때 ResizeObserver를 다시 연결해 기존 좁은 화면 색인 정책이 적용되도록 수정했다. 조직 선택기를 가리던 현상과 최초 실패 캡처를 최종 결과와 구분한다.
- 실제 공개 범위 저장 뒤 동기화에서 값이 되돌아가는 결함도 발견했다. 공개 범위 컬럼과 정본 `metadataJson.visibility`를 함께 갱신하고 변경 주체를 기록한다. 이전 컬럼만 바뀐 자료도 메타데이터와 불일치하면 복구하며 다른 문서 메타데이터는 보존한다. 정본 재계산 회귀 3개와 검색 상태 5개가 통과했다.
- 실제 열린 SSE는 회수 뒤 문서 경로/원문 payload를 전달하지 않았다. 알림 목록과 읽음 변경 응답은 원문·행위자·참조를 가리고 읽음 이력과 회수 상태를 유지했다. WebSocket은 회수 후 재구독을 거부하고 소유자의 후속 메타데이터 변경에도 비공개 경로를 보내지 않았다.
- 기존 토큰으로 DMS/SNS grant 만료 전후를 비교해 DMS 잠금 미리보기와 SNS 404를 확인했다. 실제 DB의 AI 원본 재검사 adapter도 회수된 문서/게시물을 제외했다. 외부 모델 생성·임베딩까지 포함한 RAG 인수는 수행하지 않았다.
- DMS의 기존 검색 발견 정책(제목·소유자·요약·인용/경로)은 유지한다. 권한 없는 본문/스니펫은 반환하지 않으며 파일 트리는 읽을 수 있는 문서만 표시한다. 이미 열어 둔 DMS 본문의 즉시 원격 삭제는 보장하지 않으며 회수 뒤 새 조회에서 잠금 상태를 확인했다.
