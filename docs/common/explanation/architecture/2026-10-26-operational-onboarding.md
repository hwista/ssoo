# 최초 운영 준비 화면과 검증 계약

> **이전 구현의 기록:** 이 문서의 통합 운영 준비 화면과 완료 판정은 2026-10-27 사용자 검토에서 시스템의 메뉴 구조에 부적합한 것으로 확인되었다. 기존 실행 증거는 과거 코드의 동작 기록이며 현행 완료 증거가 아니다. 기능별 재설계와 검증 상태는 [소속·서비스 접근 관리 설계](2026-10-27-functional-access-management.md)를 따른다.
> 상태: 첫 시나리오 구현·격리 환경 인수 검증 완료 · 2026-10-27

## 목표

설치 담당자가 최초 관리자를 준비하고, 플랫폼 관리자가 회사·개발팀을 등록한 뒤 담당자의 소속을 승인하고 조직/PMS/DMS 승인 권한을 위임한다. 운영자는 코드나 숨겨진 URL을 알지 않아도 화면 안내로 다음 작업을 찾을 수 있어야 한다.

## 구현 범위

- 최초 관리자: 신규 플랫폼에 한해 설치 확인 코드로 최초 계정과 활성 참여 상태를 원자적으로 생성한다. 기본 암호는 제공하지 않으며 기존 계정이 있으면 최초 설정을 닫는다.
- 운영 준비: Admin 홈에서 시작하고 회사/팀 → 담당자 계정 → 소속 승인 → 승인 권한 위임 → 준비 상태 확인 순서를 제공한다.
- 기존 사용자 신청, 반려, 취소, 재시도, 위임 회수 동선은 유지한다. 관리자 운영 준비와 개인 신청의 목적을 구분한다.
- 조직은 회사부터 이어지는 경로와 코드를 표시해 동명 부서를 구분한다.
- 담당자는 서버 검색과 페이지 이동으로 전체 사용자를 조회한다. 참여/소속 조건과 선택 불가 사유를 제출 전에 표시한다.
- 계정 활성, 플랫폼 참여, 실제 소속, 서비스 이용권은 별도 상태로 표시한다. 부서 코드가 소속 승인을 대신하지 않음을 명시한다.
- 조직의 레벨 유형은 일반적인 회사/부서/팀 선택에 맞게 채우고 기존 사용자 지정값을 보존한다.

## 인수 기준

1. 새 DB에서 테스트 코드의 직접 관리자 활성화 없이 설정 화면으로 계정을 생성하고 로그인한다. 설치 코드 오류, 설정 재사용, 동시 최초 생성은 차단한다.
2. Admin 홈에서 회사·팀 생성, 담당자 생성, 두 계정 소속 신청/승인, 조직/PMS/DMS 승인 위임을 화면으로 완료한다.
3. 사용자 100명 초과 환경에서 오래된 담당자를 검색/페이지 조회로 찾아 위임할 수 있다. 미승인·다른 조직 소속자는 사유와 다음 작업이 보인다.
4. 두 회사의 같은 이름 팀이 신청/승인/위임/현재 소속에서 구분된다.
5. 일반 승인자는 본인·타 조직·위임 한도 초과를 승인할 수 없다. 위임만으로 Admin이나 본인 서비스 이용권이 생기지 않는다.
6. 실패 시 입력이 유지되고 다시 조회/재시도할 수 있다. 완료 표시와 실제 DB 상태가 일치한다.
7. 현재 소스의 서버/5앱 빌드, 관련 테스트 및 필수 가드를 통과한다.
8. Playwright CLI로 실제 API/DB를 사용해 1440×1000과 390×844에서 검증한다. 관련 console/page/API/proxy 오류를 기록하고 미해결 오류가 있으면 완료로 판정하지 않는다.

## 실제 운영 동선

[화면별 사용 순서](../../guides/initial-operating-setup.md)를 따른다. 관리자 홈 → 운영 준비 → 회사·팀 등록 → 담당자 계정 등록 → 담당자 본인의 소속 신청 → 관리자 승인 → 조직/PMS/DMS 담당자 위임으로 이어진다.

운영 안내와 개인 신청은 목적 탭으로 구분한다. 기존 개인 신청, 서비스 신청, 반려 사유, 재신청, 취소, 위임 회수는 유지한다. 저장된 담당자 목록은 회사·팀 경로, 서비스, 최대 역할을 표시한다. 사용자 관리의 인사 부서 코드는 승인된 실제 소속과 분리한다.

## 구현 경계

- `/initial-setup` GET/POST: 최초 계정이 없는 경우만 생성. `PLATFORM_SETUP_TOKEN`이 없거나 32자 미만이면 실패하며 기본 계정·비밀번호를 제공하지 않는다. DB advisory transaction lock 후 사용자 수를 다시 검사한다. 사용자·인증 계정·활성 참여는 같은 트랜잭션에 기록한다.
- `/onboarding/approval-candidates`: 플랫폼 관리자 전용. 이름·로그인 ID·이메일을 서버 검색하고 10명씩 페이지 조회한다. 계정 활성, 참여 승인, 유효 소속을 검사해 선택 불가 사유를 반환한다. 저장 API도 조건을 다시 확인한다.
- 사용자 목록은 현재 유효한 소속만 별도 조회하며 기존 legacy 인사 조직 bridge는 변경하지 않는다.
- 최초 설정의 public 경로 추가 이외에 기존 세션·서비스 입장 정책을 완화하지 않는다. 조직/PMS/DMS 위임은 본인 이용권 및 시스템 관리자 승격과 분리한다.

## 검증 중 발견하여 수정한 문제

1. 최초 설정 proxy에서 JSON Content-Type이 누락되어 모든 필드가 빈 값으로 처리됨 → 명시적 JSON 전달로 수정하고 같은 화면의 입력을 유지한 채 재시도 성공.
2. Admin 홈에서 query만 바꾸는 클라이언트 이동이 공용 입장 화면을 다시 평가하지 않음 → 공용 앱 URL resolver를 사용하는 운영 준비 진입으로 수정.
3. 복원된 비활성 사용자 탭의 `create=1`이 다른 화면에서 등록 대화상자를 다시 열음 → 실제 `/users` 경로에서만 자동 등록 의도를 처리.
4. 회사·팀 유형을 바꿔도 분류 코드가 department로 남음 → 자동 기본값만 선택 유형에 맞추고 사용자 지정값은 보존.

## 검증 범위와 인수

- 화면은 Playwright CLI의 실제 Chromium, API는 실행한 Nest 서버, 데이터는 별도 PostgreSQL 컨테이너를 사용했다. 정상 시나리오에 API mock이나 직접 관리자 활성화는 사용하지 않았다. 100명 목록 부하 fixture와 권한 상태 변경 fixture만 별도 테스트 데이터를 사용했다.
- 뷰포트는 desktop 1440×1000, mobile 390×844. 화면 캡처는 `final-*.png`, DOM/요청 기록은 실행 폴더에 보존한다.
- 검증용 브라우저·서버 프로세스와 전용 PostgreSQL 컨테이너(검증 DB 3개)는 검증 후 제거했다. 증거 파일은 보존했다.
- 기존 Docker 서비스와 운영 DB는 변경하지 않았다. production build의 로컬 실행 검증이며 실제 운영 배포 완료를 의미하지 않는다. 빈 플랫폼 설치자는 최초 설정 코드를 공급해야 한다.
- 이 판정은 첫 시나리오(운영 조직과 승인 담당자 준비)에 한정한다. CRM/DMS 전체 출시 readiness나 모든 업무 시나리오를 통과했다는 의미가 아니다.
