# 계약 문서 생성 기록과 실제 승인 절차 검토

> 후속 결과: 사용자가 단순 내부 승인 적용을 추가 승인하여 [실제 승인자 지정·요청·처리 구현](2026-09-17-contract-internal-approval-handoff.md)을 완료했다. 아래의 미구현 표기는 당시 범위를 설명하는 이력이다.

> 2026-09-17 · 기존 승인-01 · 사용자 “일단 1번으로”로 가안 승인 · 의미 보정 구현·검증 완료
> 현재 22항목 중 19완료·3잔여 · 신규 항목 0 · 실제 운영 증거 0/5

사용자가 가안(생성 기록 의미 보정)을 선택했고 [구현·검증 결과](2026-09-17-contract-records-handoff.md)를 완료했다. 아래는 승인 전 검토 당시의 현황과 두 안을 보존한 기록이다. 아래 나안은 승인·구현 범위에 포함되지 않는다. 담당자별 실제 결재는 계속 미구현이며, 이번 작업의 완료와 구분한다.

## 확인한 현 상태

계약 문서 생성과 역할별 기록 생성은 구현돼 있다. 다만 이 흐름에서 **여러 담당자가 각자 검토하고 승인하는 절차는 구현돼 있지 않다.** 기존 문서관리 검수 결과 전체를 결함으로 재분류하지 않으며, 이 검토는 계약 문서 생성에 붙은 승인 기록의 의미만 다룬다.

| 기능·화면 | 현재 동작 | 해석의 한계 |
|---|---|---|
| 계약 문서 생성 | 초안으로 Word·PDF와 검토·첨부·승인 관련 기록을 한 번에 생성 | 문서 생성 성공이 사람의 개별 승인 성공을 뜻하지 않음 |
| 결재선 설정 | 정책 이름·버전·조직 범위·필요 역할 목록을 저장 | 이 설정에 역할별 실제 담당자를 지정하는 항목은 없음 |
| 역할별 승인 기록 | 양식 소유 역할은 시스템, 나머지 역할은 실행자 이름으로 즉시 승인 상태·동일 시각을 기록 | 역할을 여러 개 추가해도 여러 사람이 직접 승인했다는 증거가 아님 |
| 사용자·조직 연결 | 실행자의 계정·조직 정보를 조회하여 역할 기록에 연결 | 사용자 정보 연결과 결재 권한·승인 의사 확인은 별개 |
| 계약 화면의 승인 단계 | 생성된 증거 경로를 수신하면 승인 단계를 완료로 저장·재조회 | 담당자별 대기·승인·반려 과정을 확인하는 기능이 아님 |
| 계약 확정 | 별도 확정 동작에서 업무 코드·청구계획 등을 검사 | 현재 승인 기록 생성이 계약 확정을 수행하는 구조는 아님 |

기본 역할은 양식 소유자와 계약 승인자다. 추가 검토 역할을 설정하면 해당 역할에도 같은 실행자가 기록된다. 계약 화면의 동기화 인원 표기도 역할별 기록 수에 기반하므로 서로 다른 승인자 수로 해석해서는 안 된다. 이 문제는 승인-01 안에서 함께 다루며 새 승인 번호로 분리하지 않는다.

문서 접근 권한을 신청·승인하는 기존 기능은 계약 내용 결재와 별개다. 그 기능까지 미구현이라고 판단하지 않는다.

## 선택 가능한 처리 범위

두 안 모두 사용자 결정 전 제품에 적용하지 않는다. 현재 문서·코드만으로 실제 담당자별 결재가 출시 필수인지, 다른 업무 절차에서 수행되는지 확정할 수 없다.

### 가안: 생성 기록으로 의미를 명확히 표시

계약 결재를 이 서비스에서 수행할 필요가 없다는 사용자 판단이 있을 때 선택한다. 실제 승인 기능을 구현한 것으로 집계하지 않는다.

| 대상 | 승인 후 적용할 내용 |
|---|---|
| 계약 문서의 진행 표시 | 해당 영역에서 승인 단계의 완료를 `역할별 생성 기록 완료`로 설명. `담당자별 검토·승인 결과가 아닙니다.`를 함께 표시 |
| 계약 화면의 역할 목록 | 기존 이름·역할·시각을 유지하고 자동 생성 기록임을 안내. 역할별 기록 수를 서로 다른 승인자 수처럼 표시하지 않음 |
| 문서관리 결재선 설정 | `이 설정은 문서 생성 시 역할별 기록을 만듭니다. 담당자를 지정하거나 승인을 요청하는 기능은 아닙니다.` 안내 추가 |
| 새로 생성되는 기록 문서 | 생성자·생성 시각과 자동 기록의 의미를 명시. 기존 기록 파일은 일괄 수정하지 않음 |
| 기존 저장·연동 | 요청·응답 필드, 상태값, 권한, 파일 경로, 문서 생성·다운로드 및 계약 확정 조건 유지. 기존 값이 개별 승인 증거가 아님을 정본 문서에 명시 |

이 안은 표시와 설명을 바로잡는 범위다. 별도 승인 요청·담당자 지정·승인·반려 기능은 여전히 미구현이다. 사용자가 그 출시 범위를 수용하고 실제 보정·검증을 마친 경우에만 승인-01 결정을 종료한다. 필요한 기능을 미루고 완료로 바꾸는 수단으로 사용하지 않는다.

### 나안: 담당자별 실제 결재 구현

이 서비스에서 계약 내용을 결재해야 한다면 선택한다. 다음을 초기 설계 기준으로 제안하며 사용자 선택 전 확정하지 않는다.

1. **문서 생성과 결재 요청 분리.** 기존 생성·다운로드는 유지하고, 생성된 특정 문서 버전을 대상으로 별도 `결재 요청`을 제공한다. 생성만으로 새 결재가 승인 완료되지 않는다.
2. **담당자 지정.** 기존 필요 역할 순서를 이용하되 양식 소유 시스템 기록은 양식 확인으로 구분한다. 사람의 검토 역할에는 사용 가능한 실제 계정을 지정하고, 미지정 역할이 있으면 요청을 막는다. 요청자 자신을 승인자로 지정하는 것은 초기안에서 허용하지 않는다.
3. **본인 승인·반려.** 지정된 담당자가 순서대로 자기 단계만 처리한다. 승인 선택은 명시적으로 확인하고 반려에는 사유를 받는다. 다른 사람의 처리, 중복 요청, 동시에 충돌한 처리는 서버에서 차단한다.
4. **버전과 이력 보존.** 요청 당시 문서·첨부·결재선·담당자를 고정한다. 문서를 수정하면 새 결재 요청이 필요하며 이전 버전의 승인을 새 버전에 적용하지 않는다. 반려·회수·재요청과 처리자·시각·사유를 남긴다.
5. **기존 자료와 연동 보존.** 과거 자동 기록을 실제 승인으로 이관하지 않는다. 기존 요청·응답의 뜻을 조용히 바꾸지 않고 실제 결재를 별도 계약으로 추가한다. 계약 화면과 문서관리 안에 결재 상태·내 처리 대상·상세 확인 동선을 연결한다.
6. **업무 경계 유지.** 계약 확정·청구·프로젝트 인계는 현행 조건을 유지한다. 새 결재 완료를 이 업무들의 필수 조건으로 삼는 변경은 이 초기안에 포함하지 않는다. 외부 전자서명·메일·메신저 발송도 포함하지 않는다.

결재 화면·계정 지정·버전별 이력·새 연동이 필요한 기능 구현이다. 가안보다 변경 범위가 크며 현재 구현 완료로 표시할 수 없다. 나안을 선택하면 이 범위를 기준으로 상세 화면·저장 설계와 검증 계획을 먼저 확정한다. 사용자에게 추가 정책 결정이 필요한 경우 승인-01 안에서 모아서 제시한다.

## 검증 계획과 종료 조건

가안은 문서 생성 전후·새로고침·기존 기록·역할 추가 상태에서 안내와 인원 표현을 확인한다. 계약 화면과 문서관리 설정을 세 크기에서 검사하고 기존 문서 편집·저장·다운로드·권한·실패 복구를 유지하는지 확인한다. 변경 전후 요청·응답 구조·상태값도 비교한다.

나안은 위 회귀에 더해 실제로 서로 다른 계정으로 요청·순차 승인·반려·회수·재요청·무권한 거절·중복 처리·문서 변경을 검증한다. 새로고침·계정 전환·통신 실패 후에도 처리 결과와 입력이 모순되지 않아야 한다. 기존 자동 기록만 있는 문서는 결재 완료로 표시하지 않아야 한다.

이번에는 소스와 정본 문서만 대조했다. 제품 수정, 새 빌드, 실제 결재 요청, 브라우저 재검증, 운영 배포는 수행하지 않았다. 사전 검사와 문서 정합성 검사는 기능 통과나 담당자별 결재 구현 증거로 사용하지 않는다. [기존 첨부 완료 결과](2026-09-17-post-attachments-handoff.md)의 회귀 증거도 이번 계약 결재 구현 증거로 재사용하지 않는다.
