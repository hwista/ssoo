# 조직·계정·접근 권한 업무의 메뉴별 사용과 검증

> 대상: 플랫폼 관리자, 승인 담당자, 직원 · 최종 업데이트: 2026-11-05
> 신청·승인과 추가된 공통 관리 기능의 현재 로컬 검증 범위·제약은 [17개 프로그램 검증 대장](../explanation/architecture/2026-11-04-admin-program-implementation.md)을 참조한다. 아래 사용 절차 자체를 실제 실행 증거로 간주하지 않는다. 초기 신청·승인 검증은 [기존 설계·검증 대장](../explanation/architecture/2026-10-27-functional-access-management.md)에 보존한다.

## 기능별 진입점

SMTP·AI 임베딩·Microsoft 로그인은 예산 확보 후 연결하도록 보류했다. 현재 공통 관리는 기존 비밀번호 로그인으로 확인하고, 추후 설정은 [외부 연동 설정과 재개](deferred-external-integrations.md)를 따른다. 실제 외부 성공 검증은 아직 수행하지 않았다.

대시보드에 시나리오 전용 시작 버튼을 두지 않는다. 각 기능은 플랫폼의 메뉴와 직접 주소로 독립적으로 사용한다. 기본 로컬 플랫폼 주소는 `http://localhost:3000`이다.

| 메뉴 | 직접 주소 | 사용할 때 |
|---|---|---|
| 플랫폼 관리 → 조직 관리 | `/organizations` | 회사·팀을 등록하거나 기존 조직 정보를 변경할 때 |
| 플랫폼 관리 → 사용자 관리 | `/users` | 로그인 계정을 만들고 계정·참여·승인된 소속 상태를 확인할 때 |
| 내 업무 → 내 소속 | `/my-organizations` | 본인의 소속 확인, 소속/새 조직 신청, 신청 취소·결과 확인 |
| 내 업무 → 서비스 이용 | `/my-services` | 조직별 서비스 권한·역할 확인, 이용 신청, 승인된 서비스 열기 |
| 내 업무 → 신청 승인 | `/approvals` | 다른 사용자의 신청 처리, 유형·상태별 내역 조회 |
| 플랫폼 관리 → 역할 & 권한 → 승인 권한 위임 | `/roles?tab=approval-authorities` | 승인 담당자 추가·변경·회수 |

플랫폼 관리 메뉴는 관리자에게만 표시된다. 신청 승인 메뉴는 관리자와 유효한 승인 담당자에게만 표시된다. 일반 직원도 개인 메뉴를 사용할 수 있으며, 승인되지 않은 서비스에 들어가면 개인 메뉴로 이동할 수 있다. 다른 앱에서도 사용자 메뉴의 ‘내 소속’, ‘서비스 이용’, ‘신청 승인’으로 플랫폼의 같은 기능에 접근한다.

## S01: 새 회사의 직원이 업무 서비스를 사용하기까지

관리자와 직원은 다른 브라우저 프로필을 사용한다. 일반 창과 시크릿 창을 사용할 수 있으며, 시크릿 창에서 담당자/직원을 교체할 때는 로그아웃한다. 같은 프로필의 탭은 로그인 상태를 공유한다.

테스트 데이터 이름과 코드는 기존 자료와 구분되도록 정한다. 예: 회사 `테스트회사 / TEST_COMPANY`, 팀 `개발팀 / TEST_DEV`, 담당자 `test_owner`, 직원 `test_staff`. 이미 존재하는 값이면 새로운 접미사를 붙인다. 사용자 등록에는 로그인 ID, 이름, 이메일, 영문·숫자·특수문자를 포함한 8자 이상 비밀번호가 필요하다. 담당자·직원 역할은 ‘사용자’로 유지한다.

| 순서 | 실행자와 메뉴 | 처리 | 정상 결과 |
|---|---|---|---|
| 1 | 관리자 → 조직 관리 | 회사 유형·최상위로 회사 등록, 팀 유형·방금 만든 회사를 상위 조직으로 팀 등록 | 회사/팀 계층과 고유 조직 코드가 표시됨 |
| 2 | 관리자 → 사용자 관리 | 담당자·직원 계정 등록 | 계정은 활성, 실제 소속은 승인 전 상태 |
| 3 | 담당자 → 내 소속 | ‘소속 신청’에서 기존 조직·개발팀 선택, 사유 입력 후 신청 | 내 신청 내역에 승인 대기 |
| 4 | 관리자 → 신청 승인 | 담당자와 개발팀을 확인하고 처리 사유를 입력해 승인 | 담당자의 내 소속에 개발팀 표시 |
| 5 | 관리자 → 역할 & 권한 → 승인 권한 위임 | ‘승인 담당자 추가’, 개발팀 선택, 담당자 검색/선택 후 조직 승인 저장. PMS·DMS 이용 승인도 각각 최대 역할 ‘일반 사용자’로 저장 | 같은 담당자의 개발팀 조직/PMS/DMS 승인 범위 3건이 목록에 표시됨 |
| 6 | 직원 → 내 소속 | 개발팀 소속 신청 | 승인 대기 |
| 7 | 담당자 → 신청 승인 | 직원 소속 신청에 사유 입력 후 승인 | 직원의 내 소속에 개발팀 표시 |
| 8 | 직원 → 서비스 이용 | ‘서비스 신청’, 개발팀·PMS·DMS 선택, 사유 입력 후 신청 | 서비스별 대기 신청 2건 |
| 9 | 담당자 → 신청 승인 | 각 서비스 신청에 일반 사용자 역할·처리 사유 입력 후 승인 | 처리 상태 ‘승인’에서 결과 재조회 가능 |
| 10 | 직원 → 서비스 이용 | ‘상태 새로고침’, 현재 이용 권한 확인 후 서비스 열기 | 개발팀의 PMS·DMS 일반 사용자 권한과 앱 접근 확인 |

계정 생성, 조직 소속, 서비스 이용권, 승인 담당자 권한은 서로 다른 상태다. 인사 부서 코드 입력은 소속 승인이 아니며, 승인 담당자 지정은 담당자 자신의 서비스 이용권을 부여하지 않는다. 회사의 승인 권한은 하위 팀으로 전파되지 않으므로 개발팀 신청 처리에는 개발팀 범위를 지정한다.

## 기능별 예외 확인

| 확인 | 정상 동작 |
|---|---|
| 소속 없는 사용자를 승인 담당자로 선택 | 선택 불가와 필요한 조치 표시 |
| 처리 사유 없이 승인 | 버튼 비활성 |
| 담당자 본인의 신청 | 본인 승인함에서 제외, 다른 승인자가 처리 |
| 위임된 최대 역할보다 높은 역할 승인 | 서버에서 거부, 기존 신청·권한 보존 |
| 다른 조직의 신청 조회/승인 | 담당 범위 밖 정보·처리 차단 |
| 승인 대기 신청 취소 | 내 신청 내역에 취소 상태, 승인함 대기 목록에서 제외 |
| 반려 후 재신청 | 반려 사유를 보존하면서 새 신청 가능 |
| 위임 회수 | 담당자의 새 상태 조회 이후 승인 메뉴·조회 범위에서 제외, 서버에서도 처리 거부 |
| 직접 URL / 새로고침 / MDI 재선택 | 해당 기능과 권한에 맞는 화면 유지 |
| 일반 직원의 관리 URL 접근 | 관리 기능/API를 실행하지 않고 권한 안내 |
| 조회·저장 실패 | 오류와 재시도 경로 표시, 입력/접수된 결과 보존 |

## 관리자 직접 관리 기능 검증 (2026-11-04 진행 중)

17개 공통 프로그램의 전체 합격 여부는 [구현·검증 대장](../explanation/architecture/2026-11-04-admin-program-implementation.md)을 따른다. 다음 동선은 기존 메뉴에서 같은 소속·이용권·권한 원본을 관리한다.

| 확인할 작업 | 진입과 처리 | 확인할 결과 |
|---|---|---|
| 소속 배치·전보·종료 | 조직 관리의 구성원 관리 또는 사용자 관리의 소속·이용권 → 소속 | 이전 소속의 종료와 새 주 소속, 기존 조직 이용권·위임의 회수 |
| 이용권 부여·회수 | 애플리케이션 이용 관리 또는 사용자 상세의 소속·이용권 → 이용권 | 같은 사용자·조직·서비스 기록의 기간·역할·현재 효력 |
| 공통 권한·예외 | 역할 & 권한 → 조직 공통 권한 / 사용자 공통 예외 | 대상·권한·기간·사유 저장, 차단 우선과 만료·회수 반영 |
| 앱 진입 진단 | 역할 & 권한 → 권한 조회 → 대상 사용자 선택 | 5앱 진입 판정과 근거 이용권. 업무 자료별 권한과는 구분 |
| 변경 추적 | 관리 기록의 변경 이력 또는 역할 & 권한 → 감사 이벤트 → 기간·대상별 이력 조회 | 대상·운영자·결과·기간 검색, 변경 전후 값과 사유, 관련 관리 프로그램 이동 |

계정 중지는 관계를 삭제하는 퇴사 정리와 다르다. 퇴사 시 소속·이용권·위임의 남은 유효 기록을 함께 검토한다. 공통 권한 기록만으로 Admin 관리 기능이 위임되었다고 해석하지 않는다. 현재 실제 SMTP가 준비되지 않아 메일 도착은 검증하지 않았으며, 발송 비활성 상태와 모의 전송기 계약만 확인했다.

## 계정이 없는 설치 환경의 최초 관리자 설정

빈 DB에 launch migration, reference seed, trigger를 적용하고 서버의 `PLATFORM_SETUP_TOKEN`에 32자 이상 무작위 설치 확인 코드를 설정한다. 계정이 없을 때 로그인 화면은 `/setup`으로 이동한다. 설치 확인 코드와 관리자 정보를 입력한 후 로그인한다. 생성 완료 후 설치 코드는 서버 환경에서 제거한다.

기존 계정이 하나라도 있으면 최초 설정을 다시 사용할 수 없다. 기존 플랫폼은 원래 계정과 복구 기능을 사용한다. 이 과정을 시험하기 위해 기존 로컬 DB를 초기화하거나 별도 상시 미리보기 환경을 만들지 않는다.
